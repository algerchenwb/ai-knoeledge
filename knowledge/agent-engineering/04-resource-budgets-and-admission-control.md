# 04｜Agent 资源预算：调用次数、并发、费用与准入控制

一个“帮我比较十家供应商”的 Agent，可能先检索，再逐家提问，随后重试、生成报告。每一步单看都不贵，组合起来却可能不断扩大。本篇讨论怎样让整个任务有明确的资源边界，尤其说明“记录已经花了多少”和“阻止下一笔开销”之间的区别。

本文基于 Pydantic AI 的固定源码做独立中文解读；账本示例为原创教学代码，不是该框架的内部实现，也未调用真实模型。上游核验日期：2026-10-04（UTC）。不提供当前模型价格表。

## 1. 先区分六种限制

| 限制 | 控制什么 | 常见误解 |
| --- | --- | --- |
| 模型请求次数 | 一次任务最多发出多少次请求 | 一次用户提问不一定只触发一次请求 |
| 工具尝试次数 | 工具实际被尝试执行的次数 | 失败调用也可能占网络、计算和费用 |
| Token 总量 | 累计输入、输出规模 | 每轮重复传入的历史上下文也可能计入输入 |
| 费用预算 | 任务允许承担的开销 | Token 数量与费用不是固定的一一对应 |
| 并发上限 | 同时运行多少请求 | 结束一个请求释放并发槽，并不退还已花费用 |
| 速率与截止时间 | 每时间窗口允许多少请求、任务最晚何时继续启动工作 | 并发低也可能短时间内请求很多次 |

例如，同一时间只跑一个调用，若每次只需十毫秒，一秒仍可能发出很多次请求。速率限制需要时间窗口或令牌桶；并发限制需要活动请求计数。预算不是授权：额度充足仍必须先检查工具权限和审批。

## 2. 从上游源码看：检查发生在什么时刻

来源文件中的 UsageLimits 说明：请求次数在发送模型请求前检查；Token 通常依赖响应中的用量，在响应后检查。这决定了它能阻止什么。

| 固定源码中的字段或方法 | 核验到的行为 | 应用含义 |
| --- | --- | --- |
| request_limit | 默认 50；已有请求数大于等于限制时，下一请求被拒绝 | 次数边界可以提前拦截 |
| input/output/total_tokens_limit | 检查累计用量是否严格大于限制 | 等于限制本身不触发这些用量检查；未来响应仍可能突破 |
| per_request_input_tokens_limit | 限制单次输入规模，与累计输入限制不同 | 防止单轮上下文过大 |
| count_tokens_before_request | 默认 False；可启用请求前的输入计数 | 有额外开销，支持范围以此提交源码说明为准 |
| tool_calls_limit | 注释定义为成功工具调用数；check_before_tool_call 检查传入的预计调用数 | 不应直接解释为所有失败尝试的硬上限 |
| cost_limit / check_cost | 已知费用大于限制时抛错；费用不可用时可告警 | 不可用费用不能被当成“免费” |

这些是 usage.py 的字段和局部方法语义；本篇没有执行框架，也没有验证所有调用方、工具批次调度或供应商的计费路径。特别是，方法接收 projected_usage 不等于已经证明整个分布式执行过程具有原子预算预占。

输出长度无法仅靠输入预先计数完全确定。供应商输出上限可以帮助约束预计开销，但推理 Token、工具价格、缓存、服务商计费规则等仍需按真实协议核验。响应后异常不会撤销已经发生的请求和账单。

## 3. 总任务与子任务必须共用预算

把总预算 100 分给三个子 Agent，如果每个都独立得到 100，实际放大成了 300；更隐蔽的是重试时重新创建一个“预算未使用”的对象。

有两种清楚的做法：

- 共用一个账本：所有子任务与重试都从同一个 task_id 的余额申请。
- 分配子额度：父账本先预占子额度；子任务在该额度内开销，结算后将确认未使用的部分返还。

第二种不能只在配置文件里写三个数字，还需要父账本真实扣减可用余额。不要既把父任务累计用量加进去，又把已包含的子任务用量再加一遍。

Pydantic AI 的 RunUsage 提供累计和差值机制；源码说明差值可用于嵌套操作共享可变用量对象时报告新增用量。是否共享实例以及如何跨进程协调，仍是应用设计问题。费用未知的区段也要明确保留，不能仅凭已知费用合计宣称“完整账单已知”。

## 4. 并发为何需要“先预占，再结算”

假设余额 100，两个请求各预计 60。若它们同时读取余额，两者都认为可以执行，最终预计开销变成 120。这就是检查与扣减之间的竞争。

准入时应在同一个原子操作中完成：

~~~text
已确认开销 + 尚未结算的预占 + 本次预计开销 <= 总限额
并且：尝试次数未满、活动并发未满
通过后写入预占，并递增尝试次数
~~~

教学代码用一个进程内 Lock 实现原子检查与预占。多副本服务需要数据库事务、条件更新或其他经过验证的协调机制；每个副本各放一个锁无法保护共同额度。

请求完成后，按可信回执结算。预占 60、实际 35，则记录已花 35，释放差额 25。预占不是花费，不能把预占与实际同时计入同一笔账。

## 5. 预计值不是保证值

教学账本用整数“演示费用单位”；100 不是人民币、美元或真实 Token 价格。真实应用若用货币，通常采用明确精度的整数最小单位或 Decimal，记录币种、费率版本和计费来源。

预算准入依赖预计值。预计 40、实际 120 时，账本必须如实记 120，并拒绝继续启动需要额度的工作。把结果截成 100 会隐藏实际超支。

只有在预计值确实覆盖真实最大支出、所有支出都经过账本且协议可执行时，预占才有更强的总额保证。否则应把它描述为控制风险的机制。应用侧停止也不等于供应商立即停止计费，硬支付上限还需供应商或账户侧措施支持。

## 6. 费用未知时如何处理

“调用超时”可能意味着服务端仍在运行，也可能已经完成但回执丢失。此时释放全部预占并重试，可能重复花钱。

本示例区分两个维度：

- 请求活动状态：本地请求结束后释放并发槽。
- 费用结算状态：费用未知时继续保留预占，等待查询或可信回执。

因此，unknown 不是 zero。后续拿到实际费用后才能结算。未知回执不是最终回执，账本允许它被已知值补齐。

生产上还要给未知结果设置查询队列、告警与人工处理规则。若决定承担未知风险后释放额度，要保留独立的未决风险账，不能将其改写为确认未消费。本例没有实现这些恢复流程。

## 7. 尝试、成功和重试是不同计数

一次工具逻辑操作可能尝试三次才成功。若只限制成功次数，失败循环仍可能拖垮服务。因此要在真正启动前计入尝试预算；模型调用和工具调用也可以分别设限。

本例每次 reserve 都消耗一个尝试名额，后续结算不会退还该名额。不同重试使用不同 attempt_id；同一业务 operation_id 则应保持稳定，供幂等保护使用。两个标识不能混为一个。

同一个 attempt_id 再次准入会被拒绝；相同已知结算重复到达不会重复扣款；不同金额的重复回执被拒绝并应触发调查。真实回执还需绑定供应商请求号、身份、币种和证据，避免他人伪造费用。

## 8. 截止时间与预算耗尽后的产品行为

任务的 deadline 应通过单调时钟参与本地准入检查，并传递给子步骤，而不是每次重试都重新获得完整超时时间。跨进程传递截止时刻还要处理时钟差异。本文账本没有实现 deadline 或速率限制。

预算不足时，产品可以返回已经确认的结果，并注明未完成范围。例如：“已核验 6 家供应商，余下 4 家未查询；现有比较不代表全部候选。”不应让模型虚构缺失资料来补齐表格。

合理的降级流程是：停止新开销 → 等待/查询已启动工作的回执 → 保存部分结果 → 说明限制与下一步。能否切换更小模型、减少检索或请求额外额度，需要事先确定质量标准和授权范围。

## 9. 可运行账本与九项检查

[教学脚本](examples/budget_checks.py) 只依赖 Python 标准库：

~~~bash
python knowledge/agent-engineering/examples/budget_checks.py
~~~

本次在 Python 3.12.14 运行，输出：

~~~text
9 budget checks passed
~~~

| 检查 | 验证目标 |
| --- | --- |
| 等额预占 | 等于额度可接受，超出余额被拒绝 |
| 低于预占结算 | 释放确认未使用差额 |
| 未知费用后补齐 | 保留预占，已知回执到达后再释放 |
| 实际超额 | 如实记录超支并阻止继续准入 |
| 重复/冲突回执 | 相同回执不重复扣款，不同金额拒绝 |
| 子任务与重试 | 使用同一账本，尝试名额不会重置 |
| 并发槽与费用 | 活动请求结束可释放槽位，未知费用仍占预算 |
| 重复尝试身份 | 同一标识不会被再次准入 |
| 双线程竞争 | 两个 60 同争 100，恰好一个成功 |

最后一项实际启动了两个线程并用 Barrier 同步竞争；只证明这个进程内锁保护的示例，不证明多进程或数据库正确性。脚本没有真实调用、持久化、框架集成、费用查询、权限验证、deadline、速率控制或流式取消。生产实现还需要日志、崩溃恢复和对账。

## 10. 练习与常见错误

练习一：预算 100；A 预占 60，B 预占 40。A 已知花 20，B 费用未知。此时已确认 20、未决预占 40、可准入余额 40。不能把 B 的未知金额记成零后得出余额 80。

练习二：重试三次，每次实际花 5，仅第三次成功。尝试数是 3，成功数是 1，累计费用是 15。前两次失败不等于无费用。

练习三：缓存读取 Token 已包含在 input_tokens 时，不能把 input_tokens 与 cache_read_tokens 再加一次当作总输入。此固定源码将缓存和音频等细分桶视为父总量中的组成部分；真实费用仍取决于相应计费规则。

常见错误包括：每个子任务重置额度；把未知当零；响应后检查却宣称绝不超支；只计成功；用局部锁宣称多副本安全；预算耗尽就丢弃已经完成的结果。
