# 08｜Agent 批量查询：分页游标、快照一致性与完整性

用户让 Agent “比较这个区域全部门店的客流”，接口每页只返回一部分。Agent 如果只读第一页，会漏数据；如果使用不断变化的数据逐页拼接，读完也可能不是同一时刻的完整集合。

本篇讲怎样把分页查询变成可解释的业务结果。参考 Kubernetes 官方开源文档中的分块列表机制，配套为原创、单进程、内存模拟。它不是 Kubernetes 客户端，也不是数据库分页性能测试。

## 1. 一页结果不是完整任务

分页接口提供的是一个切片，不能因响应 HTTP 200 就宣布完成“全部门店”比较。Agent 应把任务状态、页面状态和业务结果分开：

| 状态 | 含义 | 用户可见描述 |
| --- | --- | --- |
| 单页成功 | 这一页有效 | 仍需检查后续游标 |
| 全部读取完成 | 按接口约定到达结束，且完整性检查通过 | 指定快照和查询范围内已读取完成 |
| 预算耗尽 | 仍有下一页但停止读取 | 已读取部分，不代表全部候选 |
| 游标/快照失效 | 原枚举无法继续 | 需要重新枚举或明确放弃一致性 |
| 下游失败 | 未得到可验证的页面 | 不能说后续没有数据 |

“全部读取完成”仍受权限范围、查询筛选和数据源覆盖影响。它不等于现实世界所有门店都存在于数据源。

## 2. Offset、Keyset、Opaque Cursor 的差异

| 方式 | 例子 | 要注意什么 |
| --- | --- | --- |
| Offset | 跳过前 100 行，再读 100 行 | 前面插入/删除会改变行位置；大 offset 可能昂贵 |
| Keyset | 按稳定顺序读取 id 大于上次值的行 | 必须有完整排序和唯一打破平局规则 |
| Opaque Cursor | 把服务端返回的字符串原样传回 | 客户端不能猜测内部结构；游标不自动保证快照 |

假设原排序为 A、B、C、D，第一页读取 A、B。此后最前面插入 X，再按 offset=2 读取，会再次遇到 B；若 A 被删除，则可能跳过 C。

Keyset 可以减少位置漂移，但若排序字段更新，或过滤条件在查询途中改变，也仍可能漏读。不能因使用了 cursor 就宣称有数据库事务快照。

业务接口应明确：游标绑定何种排序、筛选、版本和有效期，以及是否保证跨页一致性。

## 3. 从 Kubernetes 开源文档看一致快照

本次阅读的官方 api-concepts.md 说明，列表可以使用 limit 和 continue 分块；返回的 continue 为空时表示该列表枚举结束。持续沿用游标时，集合 resourceVersion 保持相同，反映同一快照，而不是每页分别读取最新数据。

这意味着后续新建、更新、删除不会被随意混入这个原始列表快照。文档还说明 continue 有有效期，快照无法继续时可能返回 410 Gone，需要从头处理。

这是 Kubernetes 所描述的特定协议保证，不是所有带 next_cursor 的 SaaS API 都具备的性质。本文未连接集群，也不验证服务端实现；只用这一机制解释业务分页应写清楚的契约。

resourceVersion 是该协议中的版本标识，不能直接把它当成可加一的页码、业务时间或通用数据库事务 ID。

## 4. 游标需要绑定查询条件和认证上下文

本示例 Context 由服务端模拟认证生成，包含租户、用户、权限版本和当前读取权限；Query 包含指标、人群类型和月份。

第一页捕获快照并记录 Context 与 Query；下一页游标只能用于完全一致的上下文。换租户、用户、权限版本、月份，都会被拒绝。当前 can_read 已被撤销时，读取旧游标也先拒绝。

教学游标是随机 UUID 字符串，服务端通过内存映射找到快照与位置。它不是把数据位置公开给模型，也不需要客户端解码。随机标识本身仍不是授权；每次都要检查上下文。

真实实现还需要完整绑定筛选、排序、字段裁剪、协议版本和权限范围。若采用无状态签名游标，要验证完整性、密钥轮换和有效期，签名也不等于加密。本文没有实现这种签名协议。

## 5. 快照示例到底保证了什么

示例 Row 为冻结 dataclass；第一页把当前 Row 列表复制为 tuple，并生成 snapshot ID。之后修改 live 列表，旧快照中的行仍不变化；不带游标的新查询会读取新 live 内容。

这是在单线程检查中的内存版本绑定，便于理解“一个任务沿用同一结果集合”。它不是数据库 MVCC，也没有处理复制期间与并发写入竞争。复杂可变对象仅转换外层 tuple 并不能自动成为完整快照，本例行对象也冻结且字段为不可变基础类型。

另外，Query 在示例中只参与绑定，不真正执行指标/月份筛选；底层数据是五条虚构 Row。因此不能把它解释为实际客流查询正确性验证。

生产还需要保证源数据快照与计算结果对应。例如“画像快照 v1”和“客流快照 v2”分别分页完成，不代表两种指标处于同一个业务截止时刻。

## 6. 页面数量不决定枚举结束

不要用“本页少于 limit 条”或“本页空列表”自行推断完成。有的协议会先扫描一段数据，再应用过滤，某页为空但仍有后续游标。

Kubernetes 文档也说明 remainingItemCount 在部分筛选情形下可能不可用；它用于集合大小估计，不能成为所有接口都必有的结束信号。

教学 collector 只在 next 为 None 时结束，允许空页带 next 继续，并检查重复游标。真实接口若用空字符串表示结束，应在适配层明确转换；本例内部约定 None，不直接消费 Kubernetes HTTP 响应。

页大小是否可中途改变也依协议决定。不要未经约定修改 limit、排序或过滤条件后继续原游标。

## 7. 重试同一页与恢复任务

网络失败时，客户端可能没有收到已经产生的页面。只读且游标语义允许时，可以重试同一个输入游标；不要先推进位置再重试，否则会漏掉失败页面。

本例对同一快照位置复用同一后续游标，同一输入游标再次读取返回相同页面内容与 next。检查验证这一行为。它不实现网络超时或自动重试。

持久恢复至少需要保存：查询与认证范围绑定、快照标识、已确认页面/行、待继续游标和任务状态。处理结果与保存进度若不原子，重启可能重复应用页面。

如果读取后还要调用写入工具，页面重放会重复产生副作用，应使用独立业务幂等键。分页游标不是写入幂等键，也不是任务批准凭据。

## 8. 游标过期不能悄悄从新快照续上

假设已经读取快照 S1 的前两页，此时游标过期。重新查询得到 S2，如果只把 S2 后半部分拼到 S1，可能混入变更后的值，既非 S1，也非 S2。

一种清晰策略是：放弃旧枚举作为完整结果，从新快照重新读取；保留旧进度用于诊断但不混合统计。另一种业务确实允许最终一致结果的策略，需要显式声明，并定义去重、更新覆盖与缺失处理。

仅按 id 去重不能恢复漏读，更不能知道哪个版本才是需要的记录。本文 collector 对重复实体 ID 直接报错，用于暴露单快照协议异常，不通过静默去重掩盖问题。

本例快照租约从第一页开始为 10 个演示时间单位，读取不会延期，恰好到期拒绝。数字不是生产建议；Kubernetes 文档的默认有效期也不能当成自建接口的规定。

## 9. 防止无限循环和无界读取

Agent 应设置最大页数、最大行数、累计字节数、deadline 与回源预算，避免错误游标或超大集合导致无限处理。

本例 collector 记录已见后续游标，重复出现会拒绝；每页 snapshot 标识变化也会拒绝。达到 max_pages 后返回 partial、reason=page_budget，并保留下一游标。

这只实现页数限制，没有实现行数/字节/总时间限制。即使有 max_pages，一页本身无限大或网络一直不返回仍会出问题；接收层和调用层还需独立限制。

真实游标与完整查询参数可能敏感，不应随意输出到模型或公共日志。可以记录内部任务 ID、页数、结果规模和错误类型，用有权限的存储保存恢复信息。

## 10. 批处理与分页不是同一个维度

分页是在一个查询结果集合中分块读取；批处理是将许多不同查询或动作合并提交。批处理接口可能出现部分成功、每项独立错误和不同完成顺序。

批量读取多个 POI 时，应按稳定实体 ID 对齐返回结果，不能假定第 i 个结果永远对应第 i 个请求。少一个结果不能把后面的指标错配给前一个 POI。

对聚合指标也要谨慎：分页面的去重人数通常不能直接相加；两页覆盖相同用户时会重复计数。总体比例通常需按统一口径累加分子/分母后再计算，而不是简单平均页面比例。前提仍是能合法、正确地取得可合并的统计。

这些属于业务设计建议，脚本仅枚举行，不执行批处理、去重人数或比例聚合。

## 11. 报告要区分部分排名与全量排名

读取 20 家门店后因预算停止，能报告“已读取的 20 家中的前五”，不能宣称“区域前五”，除非接口本身提供明确排序且足以证明这个结论。

报告至少包含范围与筛选、快照/来源时间、完成状态、已确认条数和缺失原因。一个精确的数值也可能来自不完整集合，不能让语言流畅程度掩盖范围限制。

如果允许用户继续，恢复时仍需确认游标未过期、权限未改变与原查询一致。不能先显示“完成”，再把缺失页面藏到后台默默处理。
