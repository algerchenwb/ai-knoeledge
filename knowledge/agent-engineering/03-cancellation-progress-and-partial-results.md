# 03 Agent 任务取消、进度与部分完成

> 场景：Agent 读取数据、生成报表、发布结果。用户中途点击停止，系统应阻止新动作并诚实报告已经发生的事实。
>
> 前置：[幂等与恢复](01-tool-retries-idempotency-and-recovery.md)、[人工审批](02-human-approval-and-versioned-actions.md)。本篇讨论应用机制，不代表运行环境中某个框架的统一保证。

## 1. 停止文字输出，不等于停止业务任务

用户点击停止可能只让页面不再显示模型 token。后端工具仍可能运行，数据库查询仍可能占用资源，报告也可能已经发布。

需要区分：

| 动作 | 停止的对象 | 不能据此保证 |
| --- | --- | --- |
| 关闭页面/SSE | 展示连接 | 后端任务已取消 |
| 取消模型请求 | 本次模型生成 | 之前调用的工具已撤销 |
| 设置任务取消标志 | 后续调度资格 | 正在运行的外部动作立即消失 |
| 向工具传播取消 | 合作式执行 | 第三方一定支持中断 |
| 强制终止进程 | 本地运行 | 外部服务回滚、清理完成 |

产品应把“取消请求已收到”和“任务已经停止”分开呈现。取消也不自动退还已产生的费用；计费取决于相关服务协议。

## 2. 取消标志应该从业务任务身份传递

一个任务应有稳定 task_id。取消接口确认当前用户有权限处理这个任务，记录 cancel_requested，执行器在开始新步骤、重试和恢复前读取它。

所有会启动业务动作的路径都要检查：首次运行、后台重试、人工审批恢复、worker 重启以及调度补偿。只在模型提示词写“用户取消后停止”不提供后端保证。

读取和检查必须考虑竞态：worker 读到未取消后，另一请求立即设置取消，worker 仍可能发起动作。对本地事务动作可把资格检查和写入合并；跨服务动作通常仍有窗口，要设计稳定操作身份和事后核验。

本文 mock 单进程顺序执行，只核验预设交错，不证明分布式取消原子性。

## 3. 协作式取消与检查点

合作式任务在可控位置检查取消，例如每处理一批记录、每发起一次 API、每次重试等待结束前。

检查间隔影响响应延迟：

- 每条记录检查可能开销大。
- 每个十分钟大批次只检查一次，用户会等很久。
- 拆小批次可改善响应，但需要权衡请求量、吞吐和事务边界。

阻塞型网络调用、同步 CPU 工作或第三方接口不一定能立刻中断。应设置调用超时，并使用该客户端实际支持的取消方式；不要默认取消外层 coroutine 就杀掉所有底层线程。

取消清理也应有期限，不能让“清理中”无限延长。已成功的外部写入应记录真实回执，再按需要执行单独的业务补偿。

## 4. 心跳是存活信号，不必是业务进度

心跳常用于说明 worker 仍在运行，某些框架也利用它传递取消和检测长时间无响应。

但“每秒心跳一次”不证明已经处理了任何记录。卡在无效循环中也可以持续心跳。

建议分开：

| 记录 | 例子 | 作用 |
| --- | --- | --- |
| heartbeat_at | 最近一次存活时间 | 发现失联/运行异常 |
| progress | 已核验 30/100 个对象 | 业务完成度 |
| stage | 读取、计算、等待审批、发布 | 当前阶段 |
| operation receipt | 发布结果 ID 与版本 | 权威动作证据 |

进度应在实际确认后增加，而不是在请求发出时增加。处理了 100 行也不一定意味着产物已上传；界面要说明当前阶段。

## 5. 开源案例：Temporal 的取消示例

固定快照的 hello/hello_cancellation.py 中：

1. never_complete_activity 在循环里调用 activity.heartbeat，再等待一秒。
2. 取消传入时捕获 Temporal CancelledError，打印说明后重新抛出。
3. Workflow 执行该 Activity，设置 heartbeat_timeout=2 秒及执行超时。
4. Workflow 的 finally 块安排 cleanup_activity。
5. 客户端启动工作流，等待后调用 handle.cancel，再读取最终结果。

对应测试 hello_cancellation_test.py 先等待 Activity 已启动，再请求取消；断言结果异常的 cause 为 CancelledError，且最终工作流状态为 CANCELED。

这里可学习的实现思路是：取消传播、长期 Activity 心跳、收尾动作、最终状态验证。**核验范围：**本篇阅读了源码及测试内容，没有运行 Temporal 服务，也没有执行该上游测试。

示例清理 Activity 仅打印文字。测试也没有验证真实文件清理或业务补偿完成，不能把 finally 的存在当作所有资源必然释放的证明。

hello_activity_heartbeat.py 另外展示按秒心跳与 heartbeat_timeout 的接线。本篇不把“2 秒”作为所有网络和任务的生产推荐值，也不承诺用户点取消后严格两秒停止；实际延迟还受 SDK、传输和执行状态影响。

## 6. 任务状态与操作状态分开

一项任务可以被取消，但其中第一步已成功。用一个 cancelled 布尔值会丢失信息。

本文自设状态口径：

| 任务展示状态 | 解释 |
| --- | --- |
| queued | 未开始 |
| running | 执行中，尚未最终核验 |
| cancelling | 已请求取消，仍有动作在运行 |
| cancelled | 已阻止后续动作，无已确认成功 |
| cancelled_partial | 取消后，部分动作已有成功证据 |
| cancelled_with_unknown | 某动作结果未知，仍需对账 |
| succeeded | 已达到并确认最终成功条件 |

这些名字是教学应用设计，不是 Temporal 官方状态枚举。生产还需要 failed、过期等适合自身业务的状态。

操作本身另有 pending、running、succeeded、unknown、skipped 等记录。cancelled_partial 可以展示哪些已完成、哪些跳过；不要自动把成功动作改成 failed。

## 7. 取消之后到达的成功回执

时间顺序可能是：

- worker 开始生成报表。
- 用户请求取消。
- 后端完成生成并返回 report_id。
- 系统阻止发布阶段。

此时应记录“报表已生成，发布未执行”，而不是声称“所有动作均未发生”。

如果网络超时且结果未知，应保持 unknown，之后查询得到结果再更新操作事实。对账更新事实不代表重新允许后续动作。

任务已经 finalized succeeded 后才收到取消，本例保留成功结果，不重写历史。真实业务可设计“撤销成功产物”入口，但它是新动作，不是把过去变成没发生。

“正在运行 + 请求取消”的边界也需定规则：可能允许当前原子步骤完成，再停止后续；可能尽力中断当前步骤。界面应按实际策略解释，不能提前宣布确定结果。

## 8. 旧 worker 与迟到回调

重试或换 worker 后，旧尝试的回调可能迟到。建议回调包含 task_id、operation_id、attempt_id 或 generation，并与当前允许的尝试匹配。

本文 mock 使用 generation 检查，旧 generation 回调被拒绝，避免直接覆盖当前运行状态；但生产设计应保留该回调作为排查线索。

注意另一层边界：丢弃旧回调不代表旧 worker 的远端副作用不存在。需要业务幂等和查询确认，不能因为“结果没写进本地状态”就忽略可能的重复发布。

租约与 fencing token 可用于阻止过期执行者推进受支持的资源，但只在资源端真正校验 token 时才有效。本篇没有实现分布式租约或远端 fencing。

## 9. 进度百分比的业务含义

固定 100 个对象、每个工作量相近时，可展示：

$$
progress = confirmed\_objects / eligible\_objects
$$

若任务还要上传或发布，就不能用处理对象进度直接代表全部任务完成。

对动态探索 Agent，步骤总数可能未知。此时更适合展示“已检索 8 个来源，正在核验第 3 个结论”，而非凭模型猜测“完成 83%”。

建议记录：

- 本批总量及确定总量的时间/版本。
- 已成功、失败、跳过、结果未知的数量。
- 当前阶段和最近业务进展时间。
- 产物引用与未完成动作。
- 取消请求时间、停止确认时间。

取消不应把进度强制拉到 100%。重试也不要重复累加同一对象，应按业务对象和操作回执去重。

## 10. 八个离线交错检查

[完整脚本](examples/cancellation_checks.py)使用 Python 标准库，不需框架、网络或真实账号。

| 场景 | 已验证结果 |
| --- | --- |
| 开始前取消 | 两个待执行动作跳过，新动作被阻止 |
| 执行中取消，成功回执稍后到达 | 保留已生成事实，发布被跳过 |
| 重复取消 | 只登记一次取消事件 |
| 远端结果未知时取消 | 展示 cancelled_with_unknown |
| 取消后查询得到回执 | 更新为部分完成，继续阻止发布 |
| 旧 generation 回调 | 拒绝覆盖当前操作状态 |
| 前置生成未成功就发布 | 依赖校验拒绝 |
| 成功结束后才取消 | 保留成功结果与回执 |

这些是确定性顺序调用模拟交错，不是并发压力测试。没有持久化、身份系统、真实传播延迟、强制进程退出或外部资源回滚验证。

mock 的取消跳过所有 pending 操作，已运行操作只接受可核验回执；它没有真正中断一个计算线程。generation 也没有连接到真实资源端。

~~~bash
python knowledge/agent-engineering/examples/cancellation_checks.py
~~~

## 11. 练习与答案

1. SSE 断开后能显示“任务已取消”吗？  
   **答案：** 不能仅凭断开，需要业务取消请求及后端状态证据。

2. 心跳正常，但 processed_count 一直不变，是成功进展吗？  
   **答案：** 心跳只说明存活，应检查业务进展与超时条件。

3. 取消后收到 report_id，是否丢弃它以保持 cancelled？  
   **答案：** 不应丢弃权威事实，记录部分完成并阻止后续发布。

4. 超时未知结果能改成 cancelled 且宣称无产物吗？  
   **答案：** 不能，应保持未知并查询/对账。

5. 拒绝旧回调能证明旧动作没影响第三方吗？  
   **答案：** 不能，必须核验第三方回执和幂等协议。
