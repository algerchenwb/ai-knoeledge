# 02 Agent 人工审批：绑定动作、检查版本与安全恢复

> 场景：Agent 生成九月区域报表，人工确认后才发布给指定受众。审批必须限定具体动作，不能只在聊天中记住一个“同意”。
>
> 前置：[工具重试、幂等与恢复](01-tool-retries-idempotency-and-recovery.md)。以下是独立工程设计，加上已核验开源案例；不是现成生产审批服务。

## 1. 人工审批要解决什么

模型能提出“发布给全体客户”，但业务系统应在执行前让有资格的人看到实际影响。

一次审批至少回答：谁批准、批准哪个租户的哪个动作、参数是什么、依据哪个业务版本、何时失效。不能只保存 approved=true，然后允许 Agent 继续执行任何后续写操作。

本篇以报表发布说明机制。其他场景如退款、订单修改、账号操作，都需要自己的业务规则，不能照搬同一额度和权限策略。

| 环节 | 责任 |
| --- | --- |
| Agent 提案 | 提出工具与候选参数 |
| 服务端校验 | 类型、权限、对象归属、业务前置条件 |
| 审批展示 | 清楚呈现对象、内容、受众和影响 |
| 审批记录 | 保存审批身份、动作快照、决定与期限 |
| 最终执行 | 重新核验并调用业务服务 |
| 回执 | 证明实际动作已完成 |

审批不是替代服务端验证；用户批准一个格式不合法或当前不允许的动作，后端仍应拒绝。

## 2. 提案应该是不可变快照

例如：

~~~json
{
  "approval_id": "approval-demo",
  "operation_id": "publish-report-demo",
  "tenant_id": "tenant-a",
  "tool": "publish_report",
  "arguments": {
    "report_id": "report-demo",
    "month": "2026-09",
    "audience": "internal"
  },
  "object_version": 7,
  "policy_version": 2,
  "expires_at": 100
}
~~~

本篇 expires_at=100 是教学逻辑时钟值，不是现实日期或有效期建议。

服务端应保存权威提案，审批请求只引用 approval_id，而不是让客户端重新提交一个任意提案作为事实。执行时从权威存储读取快照，再检查工具和参数摘要。

参数哈希可以帮助绑定内容，但不替代人看懂实际变化。只展示一串 SHA-256，审批人无法判断自己批准了什么。

快照应包含语义版本：相同字段在工具 v1、v2 中含义可能不同。默认值也应明确，例如空受众究竟是“不发布”还是“所有人”。

## 3. 自然语言同意如何对应业务动作

“可以”“就这样吧”可能是在评价报告文字，也可能是在同意发布。应用必须知道用户当前回应的是哪个待审批提案。

可靠的设计是让页面或接口明确选中 approval_id，展示具体动作后提交 approve/reject。审批身份来自已认证会话，不能相信模型输出中的 reviewer_id。

如果产品使用聊天交互，也应把明确的提案引用、展示内容和用户决定形成结构化记录。不能仅靠模型判断一句模糊回应，然后把旧聊天中的“同意”套到新动作上。

用户编辑参数会产生新提案或新版本：原来批准内部发布，改成公开发布后应重新审批。不能把审批视作“允许模型随便继续改”。

## 4. 开源案例：Temporal + Deep Agents 的暂停与恢复

核验的 human_in_the_loop/workflow.py 在创建 Agent 时，对 book_trip 工具设置 interrupt_on，并配置 InMemorySaver；thread_id 使用稳定 workflow ID。

控制流程是：

1. ainvoke 返回当前状态，其中可能包含 __interrupt__。
2. 工作流把待审批内容保存到 _pending。
3. pending_approval Query 暴露待审批描述。
4. 工作流等待 _resumed。
5. resume Update 接收 approve 或 reject。
6. 再用 Command(resume=...) 恢复 Agent。

resume.validator 在决定进入工作流历史前，拒绝不支持的字符串。它验证的是决定格式，不是审批人的业务权限、租户归属或参数版本。

README 说明只处理一次 interrupt；生产循环应在恢复后重新检查是否又出现待审批动作。不能认为第一次批准就永久放行所有后续工具。

两个容易误读的地方：

- run_workflow.py 会自动发送 approve，**并没有真的等待人工在页面点击**。它展示启动和恢复接线。
- book_trip 只返回“已预订”的模拟文字，没有真实旅行服务、副作用或可查订单回执。

因此这是开源可读实现案例，不是已完成的真实预订产品。suite 的插件被标为 experimental，API 可能变化；本篇未运行 Temporal 服务或模型调用。

## 5. InMemorySaver 是否能抗进程退出，要看它在哪运行

案例把 InMemorySaver 放在 Temporal Workflow 内。源码说明该状态通过工作流的确定性重放重建；它依赖这个特殊运行环境。

不能推导普通 Python 进程中的内存 checkpointer 也能跨重启保留状态。离开相应重放机制，内存随进程退出丢失。

恢复还需要稳定身份、兼容的流程逻辑和框架历史协议。应用不能在恢复时随意改变已审批动作的语义。外部业务写入仍需幂等，与工作流重放是两层机制。

## 6. 审批后执行前再核验：处理 TOCTOU

TOCTOU 是“检查时与使用时状态不一致”。例如人工审批时报告版本为 7，执行时报告已更新到 8；原审批针对的内容不再是当前内容。

最终执行至少重新检查：

| 项目 | 为什么要再查 |
| --- | --- |
| 当前认证与权限 | 审批角色可能已撤销 |
| 租户与对象归属 | 防止拿别人的提案 ID 执行 |
| 参数摘要 | 确保批准内容未变 |
| 对象版本 | 防止发布审批后被改写的内容 |
| 策略版本 | 旧规则下的批准可能不再有效 |
| 期限与取消状态 | 动作可能已过期或被用户取消 |
| 操作回执 | 防止恢复时重复执行 |

版本不符时，不应让模型“按最新版本继续”。通常是阻止本次执行，生成新提案，或采用经过业务定义的重新校验流程。

多记录条件不能只在客户端检查。业务服务应通过事务、乐观锁或等价协议将前置条件检查与实际状态改变结合。若跨服务调用，本地锁不能消除远端状态变化窗口。

## 7. 过期、拒绝和修改，怎样设计状态

简化状态可为：pending → approved / rejected / expired；approved 再进入 executing → succeeded / failed / outcome_unknown。取消也需记录，已成功的动作不因取消自动消失。

过期规则应明确相等边界。本地 mock 使用 now >= expires_at 时不允许新执行，所以恰好 100 也过期。

重复提交同一决定可以返回已有结果，反向决定或不同审批人覆盖已记录决定则需要明确业务规则。不要用“最后一次点击覆盖所有历史”掩盖竞争。

审批与执行成功是不同事件：

- approved：有资格的人批准了提案。
- succeeded：业务服务确认已执行。
- outcome_unknown：执行结果仍需查询。

审批界面显示“已批准”时，不应同时写“已经发布”，除非有执行回执。

## 8. 同一次审批如何避免重复执行

浏览器重试、Update 重复提交或工作流恢复，都可能再次触发执行。应给已审批动作保留稳定 operation_id，并由业务执行层去重。

本地 mock 将回执存到 (tenant, operation_id) 下。重复调用返回同一回执，不再产生副作用；对象版本在首次执行后增加，不应该因此把已确认的历史成功误报成“第一次没执行”。

但返回回执和发起新写入是两个路径：已过期的审批不能授权新的动作；在符合当前权限与保留规则时读取历史回执，只是在查询已完成事实。

本篇 mock 在读回执前仍核对身份、审批和参数。生产系统还要分别设计查询权限、撤销后的历史访问和隐私边界。

如果后端不支持幂等或可查回执，应保留未知状态并对账，不能靠“审批只能点一次”的前端按钮保证不重复。

## 9. 多个动作与审批范围

Agent 一次可能提出多个工具调用，例如生成报表、上传附件、通知客户。

必须定义审批粒度：

- 单动作审批：每个提案独立绑定参数和回执。
- 批次审批：审批快照包含明确的成员和依赖关系。
- 限定额度或范围的授权：仍由执行器检查每次调用是否在范围内。

批次中一个动作成功、另一个失败，应报告部分完成；不能用一个 approved 标志宣称所有动作完成。

新增成员、改变受众或改变金额属于范围变化，不自动继承原审批。读操作是否需要审批应由业务规则决定，不必为所有无副作用查询机械添加确认。

## 10. 本地示例：十个已验证场景

[approval_gate_checks.py](examples/approval_gate_checks.py)使用 Python 标准库、不可变提案、服务端字典和单进程锁，没有网络、账号或模型。

| 场景 | 已核验行为 |
| --- | --- |
| 正常批准并执行 | 副作用次数为 1 |
| 重复批准与执行 | 复用原决定/回执，不新增副作用 |
| 改成公开受众 | 参数摘要不同，拒绝 |
| 恰好到期 | 新执行被拒绝 |
| 跨租户 | 拒绝 |
| 审批权限撤销 | 拒绝 |
| 对象版本变化 | 拒绝 |
| 策略版本变化 | 拒绝 |
| 任务取消 | 拒绝 |
| 已拒绝的提案 | 不执行 |

拒绝场景副作用次数均为 0。它验证的是状态与校验顺序，不是身份系统、数据库事务或分布式并发。

mock 中 Actor 是可信测试输入，没有认证层；为简化，审批和执行检查使用同一 reviewer。真实服务可由工作进程执行，但必须核对发起人、审批人和执行身份各自的授权规则，不能拿该简化直接上线。

字典与锁没有持久化、TTL 清理或多进程协调。没有测试强制退出、并发交错、跨服务事务或实际外部动作。相同范围可以重新发起不同业务动作，必须由业务层赋予新身份，不能无限复用单次审批。

~~~bash
python knowledge/agent-engineering/examples/approval_gate_checks.py
~~~

## 11. 练习与答案

1. 人工批准内部报表后，Agent 改为公开发布，能沿用原审批吗？  
   **答案：** 不能，参数范围改变，需要新提案/审批。

2. 只验证 decision 在 approve/reject 中，就验证了权限吗？  
   **答案：** 没有，这只是格式检查。

3. 用户批准后，报告版本变化，应执行最新内容吗？  
   **答案：** 不能直接执行，需阻止或重新校验/审批，按业务协议处理。

4. 工作流等待恢复，是否保证外部动作只执行一次？  
   **答案：** 不保证，还需稳定操作身份和业务服务幂等/查询协议。

5. 示例打印 Booked 是否证明真订单已创建？  
   **答案：** 不证明，源代码是模拟返回值，应查实际业务回执。
