# 07｜Agent 外部 API 熔断：故障分类、试探恢复与隔离

Agent 为生成一份区域报告，可能查询客流、画像、竞品和地图。如果画像接口持续失败，Agent 不断重试，可能把连接池占满，连正常的客流查询也受到影响。

熔断器根据近期观察到的故障，暂时拒绝新的下游调用，经过冷却再允许少量探测。它减少失败放大，不能修复下游，也不能确认已经发出的写入是否成功。本篇基于 PyBreaker 固定源码解释机制，附独立教学状态机；不调用真实 API，不运行 PyBreaker 库。

## 1. 熔断、限流、并发、重试是不同工具

| 机制 | 主要问题 | 不自动解决什么 |
| --- | --- | --- |
| 限流 | 单位时间请求太多 | 低流量持续失败 |
| 并发隔离 | 同时运行过多，挤占资源 | 调用结束后不断再次失败 |
| 超时/截止时间 | 等待过久 | 副作用回执丢失 |
| 重试 | 短暂故障可能恢复 | 持续故障中的重试放大 |
| 熔断 | 失败达到条件后减少新调用 | 取消在途调用、保证恢复 |
| 幂等与对账 | 重复写入和未知结果 | 下游连接池容量 |

这些机制可以组合。不要收到“熔断拒绝”后立刻循环重试同一个接口；那通常只增加本地开销。也不要在每次请求中创建新的熔断器，使它永远看不到累计失败。

PyBreaker README 建议熔断器跨请求保留在应用范围，并提醒外部服务调用仍需要超时。这是实现机制建议，不是对任何业务 SLA 的证明。

## 2. 三种状态与转换

| 状态 | 新请求行为 | 转换条件 |
| --- | --- | --- |
| closed（闭合） | 正常允许调用 | 观察到足够系统故障后进入 open |
| open（断开） | 立即拒绝新调用 | 冷却期结束后，后续请求触发探测阶段 |
| half_open（半开） | 只允许受控探测 | 足够成功后闭合，失败后再次断开 |

注意电路名称：closed 表示通路正常；open 表示断开。半开不是“已经恢复一半”，只是正在收集有限恢复证据。

本教学示例采用：失败阈值 2、冷却 10 个演示时间单位、一个成功探测即可关闭。数字仅用于机制检查，不能直接作为真实系统配置。

示例没有后台定时器；到期后第一个新请求触发半开。没人请求时仍保留 open 状态，不需要为“状态显示没变”自行判断服务一直未恢复。

## 3. 哪些失败应该计入

错误分类要根据接口语义，而不是把所有非 200 或所有异常都算成下游宕机。

| 结果 | 通常需要考虑的处理 |
| --- | --- |
| 连接失败、上游超时、持续服务端故障 | 可以作为系统故障信号 |
| 参数无效、资源不在授权范围 | 通常是业务/调用方拒绝，单独统计 |
| 401/403 | 区分调用方权限问题与共同认证依赖故障 |
| 429 | 依据配额主体与 Retry-After 调整速率/等待；是否计入熔断另定 |
| 404 | 区分真实不存在与路由/版本部署错误 |
| 本地预算或截止时间拒绝 | 没有启动下游，不能冒充一次下游失败 |
| HTTP 200 但内容不符合协议 | 由适配层验证后分类，不能只看状态码 |

这些是应用设计判断。某个“业务错误”反复出现也需要告警，只是它未必适合打开整个共享服务的熔断器。

避免让模型从错误文本直接决定分类；工具适配层根据稳定状态、错误码和验证规则产生结构化 outcome。

## 4. 固定 PyBreaker 源码：排除异常的真实语义

已阅读 is_system_error：排除列表可以包含异常类型或判断函数，匹配后不作为系统故障计数。

更细的行为在 CircuitBreakerState._handle_error：不属于系统错误时，调用 _handle_success；后者重置失败计数，再执行当前状态的 on_success。半开状态中的 on_success 会增加成功计数，达到 success_threshold 后关闭。

因此，“exclude 某异常”不只是保持原计数不变。它可能重置闭合状态的失败累计，并可能贡献半开的成功阈值。选择排除规则时要确认这符合业务期望。

本教学状态机刻意采用另一种明确策略：

- closed 的 business_rejection：不增也不清零已有故障计数。
- half_open 的 business_rejection：视为恢复证据不足，重新冷却。
- success：明确下游执行并给出符合预期的结果。

这不表示上游策略错误；两者定义不同。不要把本脚本当作 PyBreaker 的同义实现或兼容替代。

## 5. 连续失败与窗口失败率要分清

此 PyBreaker 快照的正常成功处理会清零失败计数，闭合状态在 counter >= fail_max 时断开，因此是连续系统失败式阈值。但排除异常也会走成功处理，这会影响“连续”的含义。

另一些系统使用滑动窗口失败率，比如至少有足够样本后再判断失败比例。不能把“阈值 5”解释为“过去一分钟错误率 5%”。

本例在完成回执时更新计数。并发请求的完成顺序不等于启动顺序；示例没有滑动窗口、时间桶、慢调用比例或统计显著性机制。真实阈值应依据流量、可接受等待与依赖容量验证，避免低样本误判。

## 6. 冷却不是单次请求超时

PyBreaker 的 CircuitOpenState 使用 opened_at 与 reset_timeout 判断冷却期；读取 datetime.now(UTC) 进行比较。它描述何时可试探，不是给外部 HTTP 请求设置超时。

教学实现用可控计时器模拟持续时间，准入还接收任务 deadline：当前时间大于等于截止时刻就拒绝，不新增请求标识、不计下游失败。真实进程可使用单调时钟进行本地持续时间判断。

示例只检查启动时刻，不能中断已经执行的请求。真实调用还要把剩余时间传给连接/读取超时、队列等待与重试流程。恢复探测若永远不返回，本例将一直占着半开名额；生产需处理超时、取消和探测生命周期。

## 7. 半开只放行有限探测

冷却结束后，如果所有等待请求一起回源，可能再次压垮刚恢复的服务。

本例在锁内检查状态并发放 Permit，在同一 epoch 中最多一个 probe。额外请求被拒绝。最后一项检查实际启动两个线程，通过 Barrier 同步竞争，结果恰好一个探测、一个拒绝。

该保证只覆盖单进程示例。多个服务副本分别持有熔断器时，每个都可能放行一个探测；不能把“一副本一探测”说成“全系统一探测”。

PyBreaker 同步 call 在 RLock 范围内委托状态执行函数；本例只在准入和结算时锁定，外部工作位于二者之间。锁范围、异步调用和共享存储行为不同，本篇没有对这些上游路径做并发集成测试。

## 8. 旧成功回执不能关闭新一轮熔断

交错示例：

1. A 已获准启动。
2. B、C 先后失败，打开熔断器。
3. A 的旧成功结果迟到。

如果直接看到 success 就关闭熔断，新的故障状态会被旧请求推翻。示例每次打开熔断时递增 epoch；Permit 记录准入代次。finish 遇到旧代次仅消费该回执，不改变当前状态。

相同 Permit 重复结算会被拒绝，避免一个成功被计两次。这是控制状态保护，不是业务幂等或供应商回执验证；Permit 不是跨系统授权凭证。实际网络回执还需要请求身份、代次和可信来源绑定。

示例不持久化 pending，也没有崩溃恢复；若调用方未结算，待处理记录不会自动清理。生产系统需要明确回执缺失与超时处理。

## 9. 熔断范围与隔离范围如何划分

把所有 API 放在一个 breaker 下，单个画像接口故障可能让正常客流查询一起被拒绝。按每个 POI 创建 breaker 又可能造成大量对象，并让共同数据库故障难以累计观察。

可以从实际依赖边界出发：同一主机/接口族/数据库资源是否共同失效，配额是否按租户隔离，失败是否来自特定凭据。将服务故障与租户配额问题分别统计，避免一个账号额度不足让所有账号受影响。

同时做资源隔离：为重型报告、交互查询配置不同的连接/工作槽，限制队列长度与等待。熔断器只根据结果控制新准入，不自动实现这些容量隔离。

PyBreaker README 提醒，多个独立 breaker 使用 Redis 存储时需要独立 namespace。本篇未测试 Redis，也不根据“支持 Redis”宣称全局状态转换、探测租约和故障恢复已获验证。

## 10. 重试放在熔断器内外，统计会不同

如果一次 breaker 调用内部重试三次，最终失败，breaker 可能只观察到一次逻辑调用失败。若每次尝试都通过 breaker，则可能观察三次失败，并在后续尝试前拒绝。

两种方式都可能合理，但必须定义：

- 计数对象是业务操作还是物理尝试。
- 重试是否共用任务预算与 deadline。
- 下游已经打开时是否停止重试。
- 重试中的写入是否有幂等键与未知结果查询。

本例没有自动重试，只接收一个已明确分类的完成结果。参见[工具执行可靠性](01-tool-retries-idempotency-and-recovery.md)和[资源预算](04-resource-budgets-and-admission-control.md)。

## 11. Agent 降级与用户可见结果

画像接口熔断时，报告仍可以展示已核验的客流结果，并明确画像缺失。不要把未调用、被熔断拒绝或网络失败翻译成“人群为零”。

可选择备用数据源，但要核对时间、地域、坐标系、统计口径与授权；切换成功也应记录来源变化。不能只因字段名字一样就混合两种指标。

缓存降级需要说明源数据日期和过期状态，参见[工具结果缓存与新鲜度](06-tool-result-cache-and-freshness.md)。对写入操作，本地超时或熔断都不能证明此前动作未发生，应先查回执和对账。

## 12. 已运行检查、监控与边界

运行[标准库教学脚本](examples/circuit_breaker_checks.py)：

~~~bash
python knowledge/agent-engineering/examples/circuit_breaker_checks.py
~~~

Python 3.12.14，本次输出：

~~~text
15 circuit-breaker checks passed
~~~

检查覆盖：首次失败、业务拒绝保留计数、成功清零、阈值打开、断开时不新增准入、旧成功忽略、冷却前拒绝、边界时半开及额外请求拒绝、探测失败、探测拒绝、成功恢复、重复回执拒绝、截止时间拒绝、独立依赖不连带关闭，以及双线程只准入一个探测。

实际验证的是单进程原创状态机；未验证真实 HTTP 超时、服务恢复、Redis、进程崩溃、框架集成或生产吞吐量，也没有运行 PyBreaker。阈值/冷却的输入配置校验和 pending 清理在示例中未实现，不应直接部署。

监控要分开记录：真实启动次数、真实下游失败、熔断拒绝、deadline 拒绝、半开探测结果、状态转换、未结算请求与降级比例。拒绝了很多调用不代表下游错误率一定下降：部分请求根本没有发出。不要把“保护系统的拒绝”算进供应商实际响应失败分母。

练习：某用户权限不足，接口返回业务拒绝，是否应打开所有租户共用的客流 breaker？答案：不能仅凭这一条判断；先区分账号范围与共同服务故障，按定义统计。也不能因它不计入 breaker 就把请求显示成业务成功。
