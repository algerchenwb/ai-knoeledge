# 11｜Agent 速率控制：突发额度、租户配额与截止时间

Agent 批量查询十个区域，每个区域调用数个接口，失败后再重试。如果多个任务同时运行，很容易在短时间内超过下游承载或账号配额。仅限制“一个任务最多调用十次”还不够：十个任务可能同时发出一百次。

本篇结合 aiolimiter 官方开源实现解释速率机制，附原创 token bucket 准入示例。示例用可控时钟和 Fraction 计算，不等待真实时间、不访问外部接口，也没有运行 aiolimiter 库。

## 1. 请求总量、速率、并发分别管理

| 控制 | 核心问题 | 例子 |
| --- | --- | --- |
| 任务请求预算 | 整个任务最多尝试几次 | 包括子任务和重试 |
| 速率限制 | 一段时间内怎样放行新调用 | 平均每秒一单位，允许两单位突发 |
| 并发限制 | 同时占用几个执行槽 | 最多五个正在调用的请求 |
| 每日配额 | 一个计费/统计日累计多少 | 依供应商规定的日界线和主体计算 |
| deadline | 当前任务最晚何时继续工作 | 排队后可能已经无时间执行 |

平均速率不是每日配额；并发结束不自动退还速率额度。按不同 API 的成本计“单位”时，也不是在统计真实请求个数，必须说明单位定义。

示例只实现速率准入、全局/租户联合检查与启动 deadline，没有实现每日计数、并发槽、费用预算或完整超时管理。

## 2. Token bucket 的容量与补充速率

教学桶有两个参数：

- capacity：最多积存多少可用额度，也就是允许的最大突发。
- rate：每时间单位补充多少额度。

开始时满桶。容量为 2、补充速率为 1，时间 0 可以连续准入两次单位请求；第三次需要等到时间 1。长时间空闲不会无限存下额度，因为余额始终被 capacity 截断。

公式为：

~~~text
new_tokens = min(capacity, tokens + elapsed * rate)
若 tokens >= amount，则准入并扣减 amount
否则最早时间 = now + (amount - tokens) / rate
~~~

这是原创 token bucket 机制，不是对 aiolimiter 私有算法的复制。它允许短时间突发，因此不能说“任意一秒内至多一个调用”。若业务需要严格滑动窗口或固定窗口计数，应另选并核验对应机制。

## 3. 从 aiolimiter 固定源码看 leaky bucket

上游 AsyncLimiter 将自身定义为 leaky bucket。max_rate / time_period 决定泄漏速率；内部记录已占容量 _level，随 event loop 时间流逝下降，容量足够后 acquire 增加占用。

默认 time_period 为 60；文档说明可先突发最多 max_rate 的额度，随后等待容量恢复。不是“每分钟开始归零”的固定窗口。文档也提供 max_rate=1、time_period 为最小间隔的配置，用于限制突发。

上游 acquire 可以使用不同 amount；此固定源码允许 amount 在 0 到最大容量之间。教学示例则要求正整数权重，主动拒绝零、负数、布尔值、浮点权重及超过任何桶容量的值。二者接口和支持范围不同。

AsyncLimiter 的 async context manager 进入时 acquire，退出时不退还额度。等待的是速率额度恢复，不是离开代码块便“释放一个并发槽”。因此不要把它当作 semaphore。

## 4. 同时约束租户和供应商总额度

只设置租户桶，多个租户可能一起超过同一供应商账号上限；只设置全局桶，单个批量任务可能占用大部分资源。

本例一次准入要同时满足全局桶与当前租户桶。在同一个 Lock 中先补充余额、计算两者最早可用时刻，全部允许才一起扣减。若租户不足，全局桶不会先扣一份又遗漏退还。

一次等待并不会预占后续名额。两个等待方看见相同 ready 时间，真正到时仍可能竞争；应重新执行准入，不能按此前估计直接发请求。

这是单进程原子检查。多副本各有一个全局桶时，总放行量可能按副本数放大；需供应商/网关侧限制，或经过验证的共享协调。不能用进程内锁宣称跨集群一致。

tenant 参数在脚本里由调用方模拟服务端身份；它不是认证实现。真实租户身份必须来自可信认证上下文，不能由模型或用户随意填不同 tenant 来获得新桶。

## 5. 请求权重与公平性

某些重型查询占三个额度，轻型查询占一个。权重应该由服务端工具定义和参数规则决定，不能让模型自报“此次成本为零”。

aiolimiter 文档提醒，混合额度时，小请求在接近上限时更容易找到足够空闲容量。源码等待堆按 amount 再按序号排序，不能只因为使用队列就宣称所有请求严格 FIFO。

大请求可能反复等待，尤其轻型请求持续进入时。生产可以评估分队列、权重调度、租户轮转、最大等待和保留容量等策略；这些策略有吞吐与公平性的取舍。

本教学示例没有等待队列，offer 仅给出 admit/wait/reject，不保证 FIFO、加权公平或防饥饿。

## 6. Deadline 要包括排队时间

排队十秒后再给 HTTP 请求完整三十秒超时，会把用户原定总期限延长。任务应共享 deadline，准入前检查剩余时间，真正启动时再将剩余预算传给下游。

本例约定 now >= deadline 时拒绝；若预计 ready >= deadline，也拒绝。不能把恰好在截止时刻获得额度当作有执行时间。

检查是必要但不充分的：ready 比 deadline 早一毫秒，不表示请求能完成。业务可再扣除合理的执行预算和安全余量；本例没有估计调用时长。

示例只拒绝新的启动，不能中断已发出的请求，也不会因调用超时就证明服务器没有执行。写入超时仍需回执查询与幂等保护，参见[工具可靠性](01-tool-retries-idempotency-and-recovery.md)。

## 7. 下游退避提示与本地速率共同生效

下游限流后，本地桶即使有余额，也不应马上继续冲击。若供应商提供等待提示，应按其真实协议解析并绑定配额主体，然后与本地最早可用时间共同判断。

本例用 backoff_until 接收已转换好的计时截止值，不实现 HTTP 头解析。只允许把共享暂停时刻向后推进，较短提示不会意外缩短已有暂停。

全局暂停只适合明确共享的供应商限制。如果实际是某个租户或凭据的额度不足，应按正确范围隔离，避免一个账号让所有租户停摆。脚本只演示全局提示，没有实现多层退避范围。

墙上时钟格式的提示若转换为本地单调时钟时间，需要处理时钟差异；不能直接将不同来源时间戳混算。示例使用演示数值，未验证真实供应商提示或网关协议。

## 8. 重试必须重新经过同一限额

每次真正发送的尝试都应经过共享速率控制。重试时创建新 limiter，会获得新满桶，绕过限制；递归工具内部自行重试也可能漏计。

如果放行后网络失败，是否计费、是否占供应商配额取决于真实协议。保守地把已启动尝试记入本地速率，不因未收回结果自动退还；时间流逝再恢复额度。

缓存命中没有真实回源时，可不消耗该下游调用额度，但仍需权限、缓存新鲜度及其他预算检查。本地熔断拒绝也不应被冒充为一个已发送请求。

本例不包含执行函数、自动重试或回执，只验证准入的额度变化；上游调用层必须按约定在真正启动前使用它。

## 9. 等待不应撑爆队列

无限等待会积累任务、内存和连接。合理的执行器需要限制队列条数、等待时长和每租户待处理量，并清理取消/过期等待者。

先占着稀缺并发槽再等很久的速率额度，可能让其他可执行任务无法进入。资源获得顺序要结合工作模式设计，且能在取消或异常时释放适用资源；速率额度与并发槽不能用同一套退还逻辑。

aiolimiter 实现用 futures 和 event loop 定时唤醒，等待堆顶部已完成/取消项会被清理。这个源码机制不等于所有等待任务、应用队列和业务状态都自动持久恢复。

本例没有 async wait、取消、排队持久化或队列容量；调用方自行根据 wait 状态安排重新尝试，不能对 ready 时间使用无界忙循环。

## 10. 时间与 limiter 生命周期

本地速率持续时间应使用适合的单调计时来源，不依赖系统日期调整。脚本主动拒绝时间倒退，使用 Fraction 方便验证精确边界；生产应评估精度、时钟来源和存储方案。

aiolimiter 文档要求实例按 asyncio loop 创建，跨 loop 复用不受支持，可能触发警告并尝试整理等待者。不要把“尽力恢复”误解为跨事件循环安全保证。

教学 Gate 不使用 asyncio，也不是跨 loop 的替代库。它的租户桶没有数量上限/淘汰机制，不能直接用于无限租户键或公开请求参数。配置、时间与输入字段也未做完整生产级校验。

## 11. 产品与观测要区分等待、拒绝、失败

“等待额度”是尚未启动；“deadline 拒绝”是已无法在任务期限内启动；“下游失败”是实际调用后失败。它们应该有不同状态和统计，不能全部显示为 API 错误。

报告可以说明已完成范围及因额度限制未执行的范围；不能把未查询的区域计为零人口，也不能为了完成表格虚构数据。大批量任务可以显式暂停或返回部分结果，但需要有已授权的恢复策略。

观察真实放行、等待时长、超期拒绝、每租户份额、权重和下游限流响应。高吞吐同时某个租户长期饥饿，不等于成功优化。
