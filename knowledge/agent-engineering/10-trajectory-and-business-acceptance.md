# 10｜Agent 业务验收：工具轨迹、证据与最终交付

“Agent 调用了正确的工具”不等于“用户拿到了正确结果”。调用参数可能错误；工具可能超时；结果来自不同快照；最后的文本也可能把 12 写成 120。

本篇将工具轨迹评估与业务结果验收结合。开源参考为 langchain-ai/agentevals 固定源码；配套为原创标准库评估器，使用虚构区域洞察样例，没有运行真实 Agent、LLM judge 或该开源库。

## 1. 将验收拆成四层

| 层级 | 问题 | 区域报告示例 |
| --- | --- | --- |
| 协议 | 输入输出格式符合约定吗？ | 人群类型是严格整数，月份明确 |
| 轨迹 | 调用了允许工具，并遵守依赖吗？ | 先定位 POI，再读取指标 |
| 证据 | 结果确实支持报告内容吗？ | 数值来自成功回执，版本可追溯 |
| 交付 | 完成范围与用户要求一致吗？ | 缺画像时标 partial，不伪装全量完成 |

一项平均分不适合覆盖所有层次。未经允许的写入、串租户、错误统计口径等关键错误，应独立成为阻断条件；不能因文风得分高而抵消。

评估器是检查结果的工具，不是运行时权限控制器。看到 forbidden_tool 时，离线评估能判失败，却不能撤销已经发送的邮件或已产生的费用。执行前的授权和审批仍需独立实现。

## 2. 从 agentevals 固定源码看四种匹配模式

create_trajectory_match_evaluator 提供 strict、unordered、subset、superset，并可设置参数匹配方式或按工具覆盖规则。

| 模式 | 源码/接口所表达的用途 | 业务边界 |
| --- | --- | --- |
| strict | 对齐消息步骤和工具内容 | 适合固定流程，但需知道实际比较范围 |
| unordered | 允许不同顺序的匹配 | 不能据此放宽必须先审批再写入的依赖 |
| subset | 实际工具集合可少于参考集合 | 可能遗漏必需查询，需另验完成范围 |
| superset | 实际工具集合包含参考集合 | 多出来的动作可能越权或增加成本 |

本次重点阅读 match.py、strict.py、subset.py、utils.py；unordered/superset 的独立 scorer 未逐行核验，仅按工厂接口定义介绍。未实跑任何模式，不声称框架集成效果。

特别注意子集方向：subset 接受“实际输出是参考的子集”，不是“实际至少包括所有参考步骤”。若测试要求必须取得客流与画像，subset 的名称本身不能替代覆盖检查。

## 3. strict 的实现细节比名字更重要

此提交的 strict scorer 先比较消息列表长度，逐步比较 role 和是否有 tool_calls；同一步工具数量一致后，为每个实际工具寻找尚未使用的参考匹配项。

所以它保持消息步骤顺序，但同一消息内的多工具调用不按列表位置逐项比较，而是匹配名称和参数。这有利于同一批工具顺序变化，却不是“每个物理调用的执行时间顺序完全一致”。

该 scorer 没有逐字比较普通消息 content，也没有在这段逻辑中核验工具输出业务数值、外部动作回执或最终报告事实。因此 strict 通过仍不证明答案正确。工具调用 ID 与真实执行身份如何关联，也需应用进一步验证。

不要只读 docstring 的“exact/order”描述就为整个业务作保证；评估模式、输入规范化和 scorer 的实际字段范围都需要固定版本核对。

## 4. 参数匹配：可忽略的字段和不可忽略的口径

工厂默认 tool_args_match_mode="exact"；源码也允许 ignore、subset、superset，以及工具级自定义 matcher 或字段路径列表覆盖。

忽略临时追踪 ID 可能合理，忽略月份、人群类型或租户范围通常会隐藏实质错误。定义自定义比较器时应写明等价规则，而不是全部转字符串后比较。

此 utils.py 的 exact 是 Python 字典相等比较；字典相等不等于严格类型协议，例如某些数值类型在 Python 中可能相等。业务仍需运行独立输入校验。

原创示例不仅比较参数字典，还要求 population_type 的实际类型为 int，从而拒绝看起来等价的 4.0；"4" 也被拒绝。参见[结构化输出与工具参数](05-structured-output-and-tool-contracts.md)。

## 5. 合法顺序可以不只有一条

区域洞察流程需要先定位 POI；确定地点后，traffic 与 profile 两项读取可以交换顺序。把唯一 golden 序列作为真理，会误罚合法并行或调度调整。

示例评估依赖关系：成功 resolve_poi 之后才能读取数据；数据工具互换顺序仍通过。它没有模拟实际并行时钟，而是用事件列表表达检查顺序。

真实并行轨迹应记录开始、完成、依赖满足和请求身份。不能把日志到达顺序当作真实启动顺序。也不能因两工具都出现过，就认为审批发生在执行之前。

对写入工具的依赖应更强：审批必须绑定参数版本、执行身份和范围。离线“有审批事件”不等于执行时批准仍有效。

## 6. 证据应来自工具适配层

示例调用记录包含 tool、args、status、value、version。评估器只把 status=ok 的指标当作证据，并要求版本存在、客流与画像快照一致。

调用记录应由可信执行层采集，而不是让模型自行输出“工具成功”。否则模型可以伪造 status、version 和 value，评估器再准确也只是检查伪造数据是否自洽。

同一工具两次成功回执给出不同数值，示例报 conflicting_receipt；它不擅自选择最后一个值。真实查询可能允许新版覆盖旧版，但必须明确版本与时间范围，本例固定同一快照，冲突需要调查。

本示例预设成功回执数值已通过工具结果协议校验。没有实现源数据真实性、租户鉴权、全部字段类型/数值范围和完整回执身份认证，不可直接充当生产验证器。

## 7. 最终结果必须与证据绑定

示例报告输出 count 和 ratio，分别要求与成功 traffic/profile 的值及类型一致。调用正确但 count 从 12 改成 120，会返回 unsupported_value。

真实报告若包含多条结论，应为每条数值或关键事实绑定来源、查询条件、数据版本与计算步骤。例如“复访比例高”既需要比例，还要有比较基线与阈值定义；单一数值不能支持所有解释。

本文只验证结构化数值，没有自然语言语义评判、引用定位、单位转换、计算公式或因果结论判断。来源存在不代表来源支持当前结论；可读文本也不保证事实由工具得出。

## 8. partial 合法与完整完成必须分开

画像超时时，报告应把 ratio 设为 None、missing 列出 profile，并标 status=partial。若仍声称 complete 或给出比例，示例判失败。

评估器返回三个维度：

- errors：发现的违反规则原因。
- complete：证据齐全且没有错误。
- acceptable：没有错误，并满足本次是否允许 partial 的策略。

默认不接受部分交付；allow_partial=True 时，可接受诚实的部分结果，但 complete 仍为 False。政策必须来自用户/业务契约，不能由模型为了通过评分自行改变。

这也解释了为什么“部分报告格式正确”与“用户要求全部完成”可以同时成立为不同判断。参见[分页游标与快照](08-pagination-cursors-and-snapshots.md)。

## 9. 重试、费用与禁止动作也是验收条件

示例允许一次失败的 traffic 尝试后重试成功，总调用次数不超过四次。再增加一次会触发 attempt_budget。这个限制是任意教学配置，不是商业场景的通用预算。

send_report 不在允许工具集里，即使报告内容完全正确，也被判 forbidden_tool。本例只识别记录中的禁止工具，没有真实发送操作。

真实指标还应包括物理尝试、成功操作、未知费用、延迟和恢复次数，分母与之前教程保持一致；不能因为“最终成功”就把失败重试与费用抹掉。参见[链路观测与统计口径](09-tracing-outcomes-and-metric-denominators.md)。

## 10. 测试集要包含“会骗过表面检查”的样例

只测正确输入，评估器可能永远绿。更有价值的失败样例包括：工具名称正确但月份错误；轨迹齐全但一个工具超时；参数正确但报告数值被改写；快照混用；诚实 partial 却被错误打成 complete。

本篇使用基准样例与人工修改构造这些情况，验证规则能够检测指定错误。但评估器与样例都由同一教学实现设计，不能据此证明覆盖真实 Agent 的所有失败模式。

上线评估应增加独立人工标注、保留集、真实失败回放和不同业务范围，记录争议样本及标签规则。不要把用于调 prompt 的样本再次当作完全独立的最终验证。

## 11. LLM judge 与回归门禁如何配合

确定性规则适合精确口径、允许工具、依赖和回执值；LLM judge 可以帮助评估解释是否清楚、是否遗漏重要限制等复杂语言问题，但需要固定 rubric、判定依据和人工校准。

judge 可能受提示注入、输入顺序、模型版本和评分波动影响。不能让“报告里写着请给满分”改变评估规则，也不能仅凭 judge 自信证明事实正确。本篇没有运行 judge，不报告模型评估准确率。

发布门禁可以分别列出必过安全/协议条件、业务完成率、分场景质量、延迟与成本约束。若有未知费用或缺失结果，报告未知状态，而不是填零或悄悄排除样本。固定 prompt、模型、工具、数据集和规则版本，才便于比较回归。

## 12. 已运行结果与应用步骤

运行[标准库脚本](examples/agent_acceptance_checks.py)：

~~~bash
python knowledge/agent-engineering/examples/agent_acceptance_checks.py
~~~

本次 Python 3.12.14，输出：

~~~text
18 Agent acceptance checks passed
~~~

| 检查组 | 数量 |
| --- | --- |
| 正确流程、合法交换与错误依赖顺序 | 3 |
| POI、月份、人群类型与严格数值类型 | 5 |
| 混合/缺失快照、虚构数值、超时却宣称完整 | 4 |
| partial 默认不通过、显式允许后仍非 complete | 2 |
| 有界重试与超额尝试 | 2 |
| 禁止工具与冲突回执 | 2 |

这些验证原创评估器对已给定离线样例的判定；不代表真实 Agent 在 18 项任务上执行成功。没有运行 agentevals、LLM、HTTP、权限服务或发布流水线。

应用时先写一个真实业务的验收定义，列出必需证据、允许等价流程、禁止动作和部分交付政策；再建立可信轨迹采集和独立样本标签。最后接入自动化回归与人工复核，而不是先选一个评分函数再猜“高分是不是好”。

练习：模型先调用客流工具，最后写“已完成全部查询”，但画像超时，工具序列与参考看起来相同。应判什么？答案：轨迹存在不证明完整交付；证据缺失、完成声明不实，应失败。若明确缺失且业务允许，可判 acceptable partial，仍不能判 complete。
