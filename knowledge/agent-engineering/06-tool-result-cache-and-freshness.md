# 06｜Agent 工具结果缓存：租户隔离、数据新鲜度与回源

用户询问“这个区域上个月的客流”，Agent 可能在解释、追问与报告生成中反复调用同一接口。结果缓存可以减少重复计算，但如果键只写 POI ID，就可能复用另一个人群类型、月份、租户或统计版本的结果。

本篇讨论业务工具结果缓存。它与模型 KV Cache、供应商 Prompt Cache 是不同层次；也与记录工具动作是否执行过的幂等账本不同。配套为原创 Python 标准库示例，开源实现参考 cachetools 固定源码与官方仓库文档。

## 1. 哪些东西值得缓存

优先考虑无副作用、结果可重复解释的读取，例如固定版本的历史月度指标、公开静态资料或明确快照的检索结果。

| 内容 | 可以考虑的策略 | 应明确的边界 |
| --- | --- | --- |
| 已发布的历史指标快照 | 按快照版本复用 | 历史数据可能补算，日期过去不等于永久不变 |
| 当前库存或报价 | 很短的复用期，执行前再核验 | 不能拿缓存作为最终下单依据 |
| 明确“未找到” | 单独短 TTL 的负缓存 | 必须由可信查询确认，不是超时造成的空结果 |
| 超时、权限拒绝、部分响应 | 本例不缓存 | 不能伪装成业务结果为空 |
| 写入动作 | 通过幂等与回执管理 | 缓存旧响应不能替代执行状态判断 |

缓存命中后减少的是某次回源工作，不代表模型生成也免费。还要分别统计模型请求与实际工具回源；被缓存复用的结果应保留来源和时间信息。

## 2. 缓存键必须代表同一个业务问题

教学 Query 包含九个维度：

| 维度 | 为什么需要 |
| --- | --- |
| poi | 地点不同 |
| tool_version | API 或协议语义可能变化 |
| metric | 客流量与复访比例不是同一个指标 |
| population_type | 居住、工作、常驻、客流口径不同 |
| start / end | 时间范围不同，共两个字段 |
| crs | 空间协议可能不同 |
| unit | 人与千人不能直接混用 |
| data_version | 数据补算或快照更新后不再复用旧值 |

服务端 Context 另外包含 tenant、subject、permission_revision、allowed_pois。键由 Context 与 Query 的不可变对象组合构成。该做法较保守：不同用户即使权限相同也不共享命中，优先避免不清楚的共享边界。

真实参数还可能包含围栏、日期类型、分子/分母定义、时区、去重规则、数据源和排序分页。只要影响结果，就要进入语义键或由明确版本间接绑定。若缓存结果带分页，不能忽略 page/cursor 后复用第一页。

脚本的 Query 是键的教学载体，不负责完整参数校验；接入模型输出时，应先运行[结构化输出与工具参数校验](05-structured-output-and-tool-contracts.md)，再构建缓存键。

## 3. 参数规范化要保留语义

同一对象的 JSON 字段顺序不同，不必生成两个缓存键；可用稳定序列化表达等价内容。但数组是否排序、空值是否删除、大小写是否统一，不能凭方便决定。

例如，候选 POI 集合可在业务声明无序时排序；“推荐顺序”数组不能排序。缺失日期、null 日期与显式默认日期是否等价，要由协议定义。空间坐标四舍五入可能把两个不同围栏合并，必须有可接受的误差规则。

本示例使用冻结 dataclass 和 tuple，不实现原始 JSON 的规范化或摘要。生产若使用摘要键，要规定编码、版本、稳定序列化和碰撞处理；摘要不能让敏感输入自动变成匿名数据。

## 4. 缓存命中也要先检查权限

如果昨天授权的用户今天被撤权，缓存里仍有昨天的数据。读取路径必须先检查当前认证上下文，再决定是否返回命中结果。

示例的 key 方法先判断 query.poi 是否在当前 allowed_pois 中，然后才访问缓存。权限版本变化也会形成新键。tenant 或权限字段由服务端认证生成，不能让模型通过 JSON 自报“我是另一个租户”。

代码通过传入 Context 模拟可信上下文；真实系统还需从认证服务获得最新状态。若认证状态本身被长时间缓存，依然可能延迟撤权。permission_revision 只是标签，不能自行发现权限已经改变。

是否跨用户共享结果，应明确相同数据可见范围、字段裁剪和审计规则。本例选择不跨 subject 共享；它不实现 OAuth、权限数据库、令牌失效或多服务传播。

## 5. TTL 管的是复用期限，不是源数据年龄

教学正结果 TTL 为 10 个演示时间单位，负结果为 2；这些任意数字用于检查机制，不是实际产品建议。

条目保存时计算 deadline = now + ttl；读取条件为 now < deadline。恰好等于 deadline 时失效。

然而，一个源数据更新时间是昨天的结果，今天刚放入十秒 TTL 缓存，也仍是昨天的数据。需要区分：

- fetched_at：何时取到结果。
- source_as_of / data_version：源数据截止时间或版本。
- expires_at：本系统允许复用到何时。

本例保留演示 source_as_of 字段，但不验证源数据新鲜度。业务要求“截至今天”时，需要检查源数据时间与成熟范围，而不是只看缓存剩余 TTL。

cachetools 的 TTLCache 默认使用 time.monotonic，避免本地持续时间判断受系统墙上时钟调整影响。跨进程持久化不能直接把一个进程的单调时钟数值当成另一个进程的绝对时间；本例使用可控时钟，未实现跨进程过期。

## 6. 从固定开源实现看过期与清理

已阅读的 TTLCache 源码显示：构造函数默认 timer=time.monotonic；写入时调用 expire，并把到期时刻设为当前计时值加 TTL。读取和 contains 都以严格小于 expires 判断是否仍有效。

官方仓库文档进一步区分“到期不可读”和“占用内存释放”：到期条目可能等到后续修改或显式 expire 才清理。不能看到 get 返回缺失就认为缓存对象已经收回所有内存。

本教学实现每次 get/put 都扫描过期条目并删除，因此清理策略与 cachetools 不同，扫描成本与条目数有关。它适合很小的机制实验，不是高性能替代实现。

容量与过期也不同：TTL 决定可读时长，LRU 决定容量不足时优先丢弃哪个条目。示例最多两条，读取更新最近使用顺序。cachetools 文档说明默认 getsizeof 返回 1，因此默认容量表示条目数量；数量上限不等于真实字节内存上限。

## 7. 可变结果会污染后续请求

如果缓存存着一个 dict，读取方修改其中的 count，下一用户可能读到被修改后的数据。官方文档明确提醒，缓存值默认可变，使用方负责避免意外修改；自定义大小计算通常在插入时发生，修改后大小也可能失真。

示例在写入与返回时分别 deepcopy：

- 写入后修改原始结果，不会改变缓存。
- 读取后修改返回对象，也不会改变缓存。

这有复制开销，且不适用于所有对象。另一种方式是缓存不可变业务对象或经验证的序列化数据。大型报告、文件句柄和数据库连接不应不加区分地 deepcopy。

## 8. 负缓存与错误缓存要分开

确认没有匹配 POI 时，短期复用 not_found 可以降低重复查询。网络超时则只证明没有收到完整结果；权限拒绝只证明当前请求不能执行；partial 说明结果不完整。这三者不能变成“查无数据”。

示例只缓存 ok 与 not_found。timeout、permission_denied、partial 都被明确拒绝。命中 not_found 返回带状态的对象，None 仅表示未命中，不把“没有缓存”与“缓存了不存在”混为一谈。

允许缓存的状态必须来自可信工具适配层，而不是模型自行生成。脚本没有实现外部调用，put 的调用方承担结果已核验的前提。若采用错误退避缓存，应设独立协议、范围和短期规则，而不是混入正常结果。

## 9. 锁保护缓存，不一定合并回源

十个相同请求同时未命中，可能触发十次昂贵查询。这称为缓存击穿/同键回源竞争。只是用锁保护 dict，并不自动让后九个请求等待第一个结果。

cachetools 官方文档说明，cached 的 lock 保护缓存对象访问，被包装函数在锁外执行；单独 lock 仍可能有缓存 stampede。condition 可使相同键的并发调用等待已在运行的调用，降低重复回源。

这些是此提交文档中的机制说明，不代表已测试框架多线程或分布式情况。本教学脚本是单线程，不实现 lock、condition 或 singleflight。

真实合并请求还需处理超时、调用失败、等待方取消、权限范围和主请求消失。跨租户请求不得仅因 POI 相同就合并。多副本之间也需要额外协调，进程内条件变量不能自动覆盖所有服务实例。

## 10. 更新、失效与旧请求迟到写回

数据更新后可以删除相关键，也可以切换 data_version，使新请求不再读取旧版本。示例实现单键 invalidate，并验证改变 data_version 会未命中。

存在一个重要交错：旧请求开始 → 缓存失效/数据更新 → 新请求取到新版 → 旧请求迟到写回。只按 POI 存储时，旧结果可能覆盖新结果。业务键应绑定明确的数据版本，并在完成时验证回执的实际版本与请求绑定版本一致。

本例不接入真实数据源，data_version 由调用方提供，不会验证回执版本；因此不能宣称已防住迟到写回。若上游不给可绑定快照版本，还需代次/失效序号、条件写入或其他一致性设计，且明确读到的数据可能变化。

## 11. 过期数据降级要让用户看得见

某些报告允许在回源故障时展示旧快照，但应该说明来源日期、过期状态和未核验范围。“实时客流”不能在失败后悄悄返回旧缓存，仍标为实时。

可以为 stale 数据另设有限保留期和降级权限，并严格区分正常命中、过期展示与真实回源。高风险写入决策应执行前重新核验，不能因解释文本看起来完整而跳过。

本例到期就未命中，没有实现 stale-while-revalidate 或 stale-if-error。降级流程是设计讨论，不是已运行能力。

## 12. 指标与已运行检查

除了命中率，还应观察回源数量、数据年龄、按租户的错误、负缓存命中、权限拒绝和容量淘汰。命中率上升同时数据更旧，不一定是优化成功。日志不要记录完整 token、敏感原始查询或未经批准的人群明细。

运行[教学脚本](examples/tool_cache_checks.py)：

~~~bash
python knowledge/agent-engineering/examples/tool_cache_checks.py
~~~

本次 Python 3.12.14 标准库执行结果：

~~~text
21 tool-cache checks passed
~~~

| 检查组 | 数量 | 目标 |
| --- | --- | --- |
| 正常命中与复制隔离 | 2 | 原值和返回值修改均不污染缓存 |
| 身份与授权变化 | 4 | 租户、用户、权限版本各未命中；撤权拒绝读取 |
| 语义参数变化 | 8 | 协议、指标、人群、起止时间、坐标系、单位、数据版本 |
| 正/负结果 TTL | 2 | 到期之前命中，恰好到期未命中 |
| 不缓存不确定/错误结果 | 3 | 超时、权限拒绝、部分结果 |
| LRU 与显式失效 | 2 | 容量限制及单键清除 |

这 21 项检查不包括线程竞争、跨进程、Redis、实际工具调用、性能、数据源新鲜度或迟到写回；脚本不依赖 cachetools，也未运行该库。它只验证原创教学缓存的明确行为。

练习：相同 POI、月份、人群，源数据补算后版本从 v1 改为 v2，能否继续命中？答案：本例不能，因为 data_version 是键的一部分。前提是调用方获得并绑定了真实版本；把版本永远写成 default 就失去这一保护。
