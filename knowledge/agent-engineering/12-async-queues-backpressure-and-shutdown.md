# 12. Agent 异步队列：背压、取消与任务收尾

用户要求 Agent 分析十家门店，每家都要调用画像、客流和检索工具。直接为每次调用创建任务，可能一下积累几千个待执行协程；只限制同时请求数，仍可能占满内存。队列把“接受工作”和“执行工作”分开，但需要回答：排队多久算过期？取消后谁负责收尾？队列清空后报告真的完成了吗？

本文提炼 CPython 开源实现，提供原创 Python 教学示例。与[速率控制](11-rate-limits-queues-and-deadlines.md)互补：上一章检查额度准入，本章实际运行单事件循环中的等待、取消和收尾。

## 1. 三种限制各管一件事

| 控制 | 通俗理解 | 能控制什么 | 仍需另管什么 |
| --- | --- | --- | --- |
| 有界队列 | 候诊室座位 | 已入队、尚未取走的任务数 | 排队等座位的生产者数量、正在执行的任务 |
| 固定 worker 数 | 接诊窗口 | 每个 worker 串行处理时的执行并发 | 单位时间请求量、费用 |
| 速率限制 | 每分钟放行规则 | 平均速率和允许的突发 | 长请求并发、队列积压 |

例如队列容量 100、worker 5，并不表示系统只有 105 个协程：若接口每来一个请求就创建一个等待 put 的任务，额外等待者仍可无限增长。需要在入口设拒绝策略、等待期限及生产者并发限制。容量也按条目计，不按字节计；上传大文档时宜队列存引用，并额外限制大小。

## 2. 背压是让上游感受到下游变慢

CPython Queue(maxsize=正整数) 满时，await put() 等到空位；put_nowait() 则直接抛 QueueFull。maxsize=0 或负数代表无界，不能理解成不接受任务。

门店分析入口可选择短暂等待，超时后明确返回“未接收”，让用户稍后重试。批量离线任务可让生产者暂停。两种策略没有统一优胜者，关键是状态明确。不要把队列已满包装成工具调用失败，触发大量自动重试。

## 3. FIFO 描述取出顺序，不能保证完成顺序

Queue 通常先取出先入队的条目；两个 worker 各自处理，第二个任务可能先返回。报告聚合应按 job_id 和业务对象关联，不能按完成顺序猜门店身份。

源码用 deque 保存任务和等待者，并唤醒尚未结束的下一个等待者。这不是跨租户公平性保证；一个租户先占满队列，其他租户仍可能等很久。公平调度需要独立设计，不由 FIFO 名称自动提供。

## 4. 队列为空、队列收尾、业务成功是三个状态

get() 取走条目就会减少 qsize，但任务可能还在调用工具。入队会增加未完成计数，task_done() 减少计数；join() 等计数归零。

因此：

- empty() 只表示没有待取出的条目。
- join() 表示入队工作已收到对应的本地处理确认。
- succeeded、failed、unknown 等业务状态需要单独账本。

如果 worker 捕获工具错误、登记 failed、调用 task_done，join 仍然可以正常返回。报告必须检查账本，不能把 join 当成“全部工具成功”。

## 5. task_done 必须与处理责任绑定

在成功 get 之后使用 try/finally，确保跳过、失败和取消路径都做一次本地确认。get 仍在等待且被取消时，并未取得任务，不应调用 task_done。

源码只检查全局计数，额外确认在计数已归零时抛 ValueError；它不核验某个 job_id 是否被重复确认。当还有其他未完成任务时，错误的重复确认可能提前减少总数。示例第五项只验证计数为零时的拒绝，不声称队列提供每任务去重确认。

这种 finally 确认适合本地生命周期示例。持久队列若需要失败重投，必须先可靠保存失败状态或重投安排，再决定如何确认；不能照搬为持久消息系统的成功 ACK。

## 6. 取消等待入队，与取消已入队工作不同

固定源码的 put 在满队列时登记等待 Future；被取消后清理等待者并重新抛出异常。测试让队列保持满、取消等待 put，验证那个条目没有被加入。

但 put 一旦成功，随后取消调用者不会自动从队列撤回条目。边界竞争时应查询接收回执，不能仅凭客户端收到取消就断言服务器未接收。工程上使用 job_id、接收状态和幂等键，把“提交结果未知”留给查询和对账。

## 7. 取消等待取出，与取消正在执行不同

get 在空队列等待时被取消，不应消费后来到达的任务；源码清理等待者。第三项实际检查取消一个等待消费者后，另一个消费者仍可取得新条目。

worker 已取得任务并开始外部操作后，取消只是对本地协程提出请求。外部 API 可能已经完成写入，不能登记“已回滚”。教学 worker 保守记 unknown，并重新抛 CancelledError；生产系统需要回执查询、幂等和补偿，见[工具可靠性](01-tool-retries-idempotency-and-recovery.md)。

## 8. 逻辑取消可以保留条目并跳过执行

已排队工作可先登记取消标记，worker 取到时跳过工具并确认本地处理。这样避免直接修改 Queue 内部 deque 或未完成计数。

示例 Job.cancelled 是同事件循环的内存字段，只在执行前检查一次。它不支持跨进程取消、不阻止检查后才到来的取消，也没有授权判断。真实系统应通过受控接口和状态版本更新账本；逻辑取消、worker 任务取消、外部操作取消需要分别记录。

## 9. 排队时间要计入业务截止时间

假设用户总共愿意等 20 秒，排队已经 18 秒，调用工具时不应再重新给 20 秒。使用同一个 deadline，并在入队和执行前检查剩余时间。

事件循环的 loop.time() 是本地单调时钟。asyncio.timeout_at(deadline) 使用它的绝对时刻；这种数值不能直接当跨机器时间戳发送。跨服务期限需要定义传输协议，并考虑时钟与网络延迟。

示例只检查“开始执行前已过期”并跳过工具，没有在 operation 内强制超时，也没有跨服务传播。第十项独立验证实际入队等待的 timeout，二者不要混为全链路限时。

## 10. 超时与取消都依赖协作

asyncio.timeout 在当前任务中使用取消机制，退出上下文时把对应取消转成 TimeoutError，应在上下文外捕获。CancelledError 继承 BaseException，普通 except Exception 不会吞掉它；清理后一般继续抛出。

阻塞事件循环的同步代码会延迟取消；wait_for 还会等待被取消任务实际收尾，实际耗时可能超过 timeout 参数。超时不是外部事务自动撤销，也不是任意 Python 代码的硬停止保证。

## 11. TaskGroup 能收拢子任务生命周期

TaskGroup 退出时等待子任务。一个子任务出现非取消异常，组会取消其余任务，等待收尾，再报告异常组。这适合基础设施严重故障时让一组相关任务一起结束。

普通某一家门店工具失败，可能应登记失败并让其他门店继续；致命账本故障则可能应退出整个组。示例 worker 捕获普通 Exception 并登记 failed，这是教学策略，生产代码应缩小可恢复异常范围。第十一项另外验证 TaskGroup 的失败传播和兄弟任务 finally，不声称示例 worker 自带生产故障分类。

## 12. 正常停机必须先停止接收，再处理已接收任务

常见流程：关闭入口并等待已有生产者结束；等待队列 join；向每个 worker 放一个结束哨兵；等待 worker 退出；核对业务账本。

停止接收是前提，否则 join 返回后仍可出现新任务。哨兵本身也进入队列计数，需要 task_done。第十二项实际使用一个 worker 和两个任务验证此流程；多 worker 应发送对应数量的哨兵。

故障停机则应设置收尾期限、登记仍未完成的任务，并执行明确的重投或人工处理策略。Queue 不是持久存储，进程崩溃不会自动保存条目、结果或确认状态。
