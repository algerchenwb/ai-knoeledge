# 05｜Agent 结构化输出与工具参数：格式、语义和权限三道校验

模型输出一个看起来规整的 JSON，距离“可以执行查询”仍有几步。它可能把客流类型写成字符串，把日期写成不存在的二月三十日，把 BD-09 坐标标成 GCJ-02，或者请求当前账号无权查看的 POI。

本篇用“区域洞察查询”解释输入协议与结构化输出。业务标识和坐标均为虚构教学数据；本文不访问真实业务接口。开源来源为 Pydantic 官方仓库固定提交，配套代码实际使用本地 Pydantic 2.13.5 验证；上游文档快照与本地包版本分别记录，不宣称两者完全同版。

## 1. JSON 能解析，不代表业务能执行

可以把校验分成四层：

| 层级 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 完整消息与解析 | 消息完整吗？是不是可接受的 JSON？ | 截断、重复键、NaN、超大消息 |
| 类型与字段约束 | 字段存在吗？类型、范围与枚举正确吗？ | population_type 必须为整数 1..4 |
| 业务语义 | 字段之间的组合成立吗？口径正确吗？ | 起止日期有序，包含首尾不超过 90 天 |
| 身份与权限 | 这个账号此时允许执行吗？ | POI 必须在服务端认证得到的范围内 |

每层都通过才进入工具执行。JSON Schema 是协议描述的一部分；它本身不会读取租户权限表，也不会保证某个经纬度的坐标系标注真实。

供应商提供的结构化生成能力可以帮助模型遵循格式，但工具执行器仍要独立验证。本文没有测试任何供应商的 Schema 支持、约束解码、拒绝响应或流式行为，不能将本地验证结果当作远端模型遵循率。

## 2. 用小而明确的业务协议约束模型

教学输入如下：

~~~json
{
  "schema_version": "insight-query.v1",
  "poi_id": "POI-001",
  "population_type": 4,
  "metric": "visitor_count",
  "start_date": "2026-09-01",
  "end_date": "2026-09-30",
  "center": {
    "lng": 116.4,
    "lat": 39.9,
    "crs": "GCJ-02"
  }
}
~~~

这里只允许两个教学指标：visitor_count 与 repeat_visit_ratio。模型负责从用户表达中选择允许的意图；服务端负责将意图路由到固定实现。不要让 metric 变成任意 SQL、内部函数名或自由拼接 URL。

POI-001 的格式匹配只能证明“形状符合约定”，不能证明地点存在。实际执行仍需查询业务数据，验证 POI 与中心点的关系；脚本没有实现真实性核验或坐标转换。

## 3. 严格类型：字符串、布尔值和整数要分清

上游 strict_mode.md 说明，Pydantic 默认可能做类型转换。例如数字字符串可被转换成整数；严格模式会减少这些转换。

示例将模型设为 strict=True，并对 population_type 使用 StrictInt：

~~~python
population_type: Annotated[StrictInt, Field(ge=1, le=4)]
~~~

以下三个输入都被示例拒绝：

- "4"：字符串。
- 4.0：浮点数。
- true：布尔值，不能借 Python 中 bool 与 int 的关系冒充业务分类。

严格并不等于所有类型都只接受完全相同的 Python 类。上游特别指出，直接 JSON 验证与 Python 对象验证可能采用不同规则，例如 JSON 中的日期可以用字符串表示。本例主动将日期定义为规范字符串，然后验证真实日历日期；不依赖隐式日期转换。

是否允许类型转换应按接口约定决定。已有 API 依赖字符串数字时，直接切严格模式可能破坏调用方；可以在明确的边界适配层转换并记录，再送入严格模型。不要让适配层随意猜测单位或业务含义。

## 4. 缺失、null、默认值、额外字段不是一回事

本例所有业务字段必填且不接受 null。人口类型缺失表示没有给出；null 表示显式空值；二者都不能默认为“客流”，否则查询口径被悄悄改变。

Pydantic 官方 models.md 说明，默认额外字段通常被忽略。因此本例在外层和嵌套 Point 都设置：

~~~python
model_config = ConfigDict(strict=True, extra='forbid', frozen=True)
~~~

意外出现 tenant_id、debug_sql 等字段会被拒绝，而不是静默丢弃。错误反馈可以提示调用方协议不匹配。若业务确实需要扩展字段，应显式定义版本或扩展容器。

上游 validators.md 还说明默认值不会自动验证，除非启用相应配置。因此重要默认值也应纳入协议审阅；不能因字段写了约束就假定所有默认路径都被检查。本例不用业务默认值。

## 5. 字段规则与跨字段规则分别写

单字段日期检查使用 field_validator，在基础类型检查后调用 date.fromisoformat。正则只能保证文本形状 YYYY-MM-DD；真实日历校验才能拒绝 2026-02-30。

跨字段规则使用 model_validator(mode='after')：

~~~python
days = (end - start).days + 1
if not 1 <= days <= 90:
    raise ValueError("inclusive date window must be 1..90 days")
~~~

加一表示包含首尾；同一天查询为一天，而不是零天。业务若采用半开区间，需要另写口径。本例验证区间有序和长度，没有验证数据是否已经成熟、是否允许未来日期或时区切日规则。

上游文档说明 after 校验器在内部校验后运行，并要返回验证后的值/实例。before 校验器处理原始输入，仍需面对任意输入；plain 校验器则可能直接结束校验，跳过内部字段类型检查。不要为了“修复模型输出”写一个原样返回的 plain 校验器，然后误以为字段仍受到 int 类型保护。

## 6. Schema 能表达多少，服务端还要做多少

脚本调用 model_json_schema，并检查外层及 Point 都有 additionalProperties=false，population_type 有最大值 4。

但是 Python 自定义的“首尾包含且不超过 90 天”规则不会自动被完整编码到生成的 JSON Schema 中。Schema 可要求两个日期字符串符合正则，仍可能允许结束日期早于开始日期。

因此同一份模型有两个用途：向模型说明可生成的结构；在服务器本地执行完整校验。服务端后者不能省略。向不同供应商传送 Schema 时，还需核对其支持的关键字和嵌套结构；本篇不声称所有供应商接受此 Schema。

协议变更也要显式处理。本例仅接收 insight-query.v1，v2 被拒绝。迁移时分别定义版本模型与转换函数，再验证转换结果；不要简单改一个版本字符串就把旧字段当成新口径。

## 7. 坐标和比例必须带含义

lng、lat 的范围约束只能排除明显非法值。两数均在范围内时，对调可能仍然合法；声明 GCJ-02 也不意味着数值确实从该坐标系取得。

真实位置查询应验证经纬度顺序、来源、坐标转换记录、围栏及地点一致性。GCJ-02、BD-09、WGS84 不能只改标签。本例把 crs 限制为 GCJ-02 并拒绝 BD-09，但没有验证数值来源。

同理，repeat_visit_ratio 不只是“一个 0..1 浮点数”。结果协议还需绑定分子、分母、去重规则、时间范围和人群口径。0.23 与 23% 可表达同一比例，直接把 23 当 0..1 比例会出错。分母为零时应返回定义明确的不可计算状态，不能强行写零。

以上属于应用设计建议；本篇脚本只实现查询输入，不实现比例计算或结果协议。

## 8. 身份必须来自认证上下文

脚本的 validate_command 接收 allowed_pois，由调用方模拟服务端认证得到的不可变集合。模型 JSON 不包含身份字段，也不能自行声明权限。

格式合法的 POI-002 仍会被拒绝，因为演示账号仅允许 POI-001。这一检查独立于 Pydantic 字段校验；框架不能替应用猜测权限规则。

生产还需绑定认证主体、租户、接口 scope、有效期和资源范围，并在执行前重新检查。读取权限不等于写入权限，预算充足不等于获得授权。拒绝原因返回给模型时，通常只给必要错误类别，不暴露其他租户数据或内部权限详情。脚本没有实现 OAuth、权限数据库或审批链。

## 9. 完整消息、重复键和非标准数值

示例先做 UTF-8 字节数限制，再用 json.loads：

- object_pairs_hook 拒绝重复键，包含嵌套对象。避免“两个 poi_id，不同组件取不同值”。
- parse_constant 拒绝 NaN/Infinity 等非标准常量。
- 截断 JSON 会解析失败，顶层数组会在模型校验失败。
- 完整对象解析后才进行类型与语义验证。

4096 字节是本教学协议的任意小上限，不是通用最佳值。真实 HTTP/SSE 服务还需在接收层限制消息体、递归深度、时间和累积流长度；本例字符串已在内存中，不能替代网络接收限制。

不要一看到流里出现右括号就执行工具；它可能是嵌套对象结束。若一个上游协议明确支持多个完整工具调用，按该协议逐个验证完整单元；本例只接收单个完整 JSON 文档。

## 10. 校验失败后：分类反馈与有限修复

错误可以分成解析、类型、业务规则、权限和运行状态几类。可修复的格式错误可向模型返回必要的字段位置与规则，并限制修复次数；权限拒绝不能靠换个 POI ID 或伪造 tenant_id 自动绕过。

服务端不能悄悄把超过 90 天的查询裁剪成 90 天，却仍声称完成原任务。应明确说明限制，或按已授权规则拆分并检查预算、去重和合并口径。

也不要在本地校验器内部查询外部 API 并产生业务副作用。校验应形成待执行命令，随后通过权限、预算、审批和幂等控制再执行。重试生成与重试执行是两种不同操作，应分别记账。

## 11. 冻结对象与执行快照

示例将外层命令和嵌套 Point 分别冻结，普通字段赋值会被拒绝。这样可以减少验证后代码无意修改参数的机会。

上游将此称为有限的不可变性：外层 frozen 不会自动冻结任意 dict/list，也不是阻挡恶意 Python 代码的安全沙箱。示例没有可变容器字段，但仍不能把 frozen 当作完整授权证明。

需要人工审批时，保存经过校验的命令快照、协议版本和摘要；执行前核对批准的内容与待执行内容一致。参见[人工审批与版本化动作](02-human-approval-and-versioned-actions.md)。不要用跳过验证的 model_construct 接收不可信模型输出；上游 models.md 明确它不运行验证。

## 12. 已运行示例与结果

[完整脚本](examples/structured_output_checks.py) 依赖 Pydantic：

~~~bash
python -m pip install pydantic==2.13.5
python knowledge/agent-engineering/examples/structured_output_checks.py
~~~

本次使用已有环境运行，并未重新安装依赖。Python 3.12.14，结果：

~~~text
23 structured-output checks passed; pydantic=2.13.5
~~~

检查组成：1 个有效命令；16 个无效对象（类型、空值、范围、额外/缺失字段、指标、版本、日期、坐标和越权）；4 个无效原始消息（重复键、截断、超大消息、数组）；1 个嵌套字段修改；1 组生成 Schema 断言。总计 23。

检查证明本地教学验证器在这些输入上的行为；没有运行 LLM、HTTP、数据库或生产权限服务，也没有覆盖全部 JSON 输入与 Pydantic 特性。脚本中的 assert 用于检查结果；运行时业务校验通过明确异常实现，不依赖可被 -O 禁用的 assert。

练习：如果模型输出“过去 90 天”，服务端仅检查区间长度是否足够？答案：不够。还要定义截止日、时区、是否包含当天、数据成熟范围；这些不是整数 90 自身能表达的口径。
