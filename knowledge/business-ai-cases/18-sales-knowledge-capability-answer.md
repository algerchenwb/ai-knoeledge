# 售前知识库答复：把产品能力、适用条件与证据一起交付

客户问“你们能导出区域分析结果吗”，售前需要回答的是这位客户在指定产品、套餐、地区和部署方式下能否使用。只检索到一页含“导出”的文档，不能直接回答“支持”。那一页可能是旧手册、内部预览，甚至只是研发规划。

本篇在[需求与能力匹配](06-sales-capability-matching.md)基础上，补齐知识版本与答复条件，适合售前助手、产品客服、招投标问答和客户成功知识库。开源机制参考LlamaIndex；能力判定策略与示例由本知识库独立编写，全部产品与资料ID虚构，不代表真实公司承诺或成功部署证明。

## 1. 先把客户问题变成可核对的业务问题

原问题：“能不能自动生成并导出我们的分析报告？”至少含两个能力：生成报告、导出报告。不能用导出能力的证据覆盖自动生成能力。

先拆成`product=atlas, capability=export`等稳定标识，再确认客户上下文。产品标识由产品目录解析，套餐来自经授权的账户服务，地区和部署方式必要时询问客户。模型可以提出候选，但不能把“应该是专业版”写成账户事实。

本文程序只接受明确的产品和能力ID，不实现自然语言拆分。真实开发时可以将提问映射接在[对象解析](16-business-object-resolution.md)之后；把证据检查接在[结果协议](17-business-result-contract.md)之前。这些是推荐集成位置，三个教学脚本尚未接成一套系统。

## 2. 把一段文档拆成一条可审核事实

假设资料写：“自九月起，专业版在中国区提供导出功能。”建议保存以下字段，而不是只保存整段向量。

| 字段 | 例子 | 解决的问题 |
|---|---|---|
| product / capability | atlas / export | 绑定具体产品与能力 |
| record_id | export-v2 | 区分事实修订 |
| state | supported | 区分交付、规划与明确未支持 |
| review | approved | 草稿不成为外部答复依据 |
| audience | public | 内部预览不外泄 |
| start / end | 2026-09-01 / 空 | 判断某天是否生效 |
| requirements | plan=pro, region=CN | 给出客户适用条件 |
| evidence | release-2#export | 关联可复核来源位置 |

实际生产还应记录源文件版本、内容哈希、文档所有者、审核人、页码或段落位置、采集时间和撤回状态。本文精简示例没有实现这些字段。不要让模型生成一个看起来像真凭实据的文档ID；证据标识应由接入服务生成，并能回到原始内容。

产品事实库应由产品负责人审批。客户邮件和销售笔记可以成为待审核线索，不能自动提升为正式产品事实。“某客户已经在用”也不能证明全部客户在全部地区都能用。

## 3. 先筛选有效资料，再比较相关程度

检索业务上常有两类条件：一类是“是否有资格参与答复”，例如产品、可见范围、审核状态和生效日期；另一类是“和问题有多相关”，例如语义相似度。相似度最高的草稿仍然不能成为已交付能力的依据。

推荐顺序是：绑定身份与产品范围，限制可见资料，筛选有效批准版本，再做关键词/语义检索与重排，最后判定支持状态。范围过滤必须由服务端执行；提示词中的“请不要泄漏内部文档”不能代替过滤。

本文`CapabilityBook.answer`对一份已提供的事实集合执行精确ID查找与过滤，没有实现RAG、Embedding、向量数据库或重排。在真实系统中，检索召回不足也会导致“未找到证据”；必须在评测中区分事实库缺失和检索漏召回。

## 4. “最新版”与“当前有效版”是两个概念

夹具包含三条导出记录：

| 记录 | 生效区间 | 状态与条件 | 是否用于2026-10-05外部答复 |
|---|---|---|---|
| export-v1 | [2026-01-01, 2026-09-01) | 已批准，basic套餐 | 否，已经到期 |
| export-v2 | [2026-09-01, 无结束日期) | 已批准，pro且CN | 是 |
| export-v3-draft | [2026-09-20, 无结束日期) | 草稿，无条件 | 否，尚未批准 |

区间采用起始日包含、结束日不包含。因此九月一日只使用v2，不会让v1与v2同一天都生效。输入日期在教学中可以自由指定；生产实时答复应由服务端绑定可信日期，历史回溯则明确标注“截至某日”，避免以历史支持替代当前支持。

日期应与产品发布地区的业务时区一致。例子使用日期，不实现小时级灰度、时区切换或分批租户放量。只有`start`不能充分表达灰度发布，正式平台还要查客户是否在已发布名单中。

## 5. 条件满足之前，不能输出“可以使用”

`export-v2`要求`plan=pro`和`region=CN`。条件检查相当于两道门，必须同时通过。

| 已知客户信息 | 结果 | 给客户的草稿表达 |
|---|---|---|
| pro、CN | supported | 该产品在专业版中国区支持导出，依据为release-2对应段落 |
| pro、地区未知 | needs_info | 已确认专业版条件，还需确认使用地区 |
| basic、CN | not_applicable | 当前套餐不满足此能力的适用条件 |
| basic、地区未知 | not_applicable，附缺失地区 | 套餐条件已不满足，地区信息也尚未确认 |

缺字段和不满足字段分别返回，避免把未知误判为不支持。本文优先返回已知不满足条件，同时保留缺失项；这样销售不会只补问地区，却忽略套餐本身已经不适用。

这里把套餐条件简化为精确相等。真实套餐可能存在能力继承、单独购买权限、合同例外和地区白名单，应由确定性权益服务计算；不要把“套餐等级更高”直接推导为功能必然开放。

## 6. 用明确状态表达知识缺口

| 状态 | 意义 | 应做的后续动作 |
|---|---|---|
| supported | 当前批准证据有效，已知条件满足 | 输出带条件与出处的能力答复草稿 |
| needs_info | 存在能力证据，客户条件未补齐 | 只问缺失字段 |
| not_applicable | 至少一个已知条件不满足 | 说明条件差异，交由售前讨论方案 |
| planned | 批准资料将其标为规划 | 明确尚未交付，不推断发布日期 |
| unsupported | 有效批准资料明确未支持 | 说明当前限制，记录需求 |
| insufficient_evidence | 没有可用资料或证据字段为空 | 核查知识库，转产品负责人 |
| conflict | 同能力存在多条同时有效的批准记录 | 暂停承诺，处理资料冲突 |

“没搜到”不是“明确不支持”。前者说明系统没有足够依据，后者必须有批准资料明示。规划中的功能也不能说成“我们可以做”，除非业务流程另外产出经过审批的定制方案。

输出示例不包含自动对客发送。先形成内部草稿，遇到方案、交期、报价或合同承诺时进入相应人工审核流程。不能因为事实查询成功，就认定对外商务承诺也已获授权。

## 7. 遇到矛盾证据，停止自动拍板

如果同一产品能力有两条重叠的批准事实，一条写支持，一条写不支持，不能让模型选语气更肯定的一条，也不能用相似度高低决定真伪。

本文保守地将任何多条同时有效记录判为`conflict`，即使文字含义可能相同；它没有实现去重或按合同例外的优先级合并。产品负责人应确定哪个版本取代哪个版本，修正生效结束日期或补全范围后，再恢复自动答复。

真实库若允许不同套餐各有一条事实，需要建立正式的适用范围与优先级规则。未经定义，不应通过“先按客户条件过滤”偷偷隐藏彼此矛盾的产品事实。

## 8. 证据存在、证据有效与证据支持结论分别验证

示例只检查`evidence`是否为空，并输出ID。`release-2#export`是虚构标识，不是可以点击的真实发布说明，因此程序通过不代表证据已查证。

生产校验至少分三步：来源服务确认引用存在且调用者有权读取；比对文档版本或哈希确认内容未被替换；根据引用段落核查它是否支持当前能力与条件。最后一步需要确定性字段核对与人工金标准评测，不能只做URL可访问检查。

模型生成自然语言时应保留条件、日期和限制，不能把“当前套餐不适用”改写成“产品不支持”，也不能把“规划”改成“即将上线”。建议同时保存结构化判定和外部草稿，抽检两者是否一致。

## 9. 如何连接开源检索框架

[LlamaIndex固定提交README](https://github.com/run-llama/llama_index/blob/962940ddc079cc21701d28d1237c84c82a7c5164/README.md)展示文档加载、构建`VectorStoreIndex`、通过查询引擎提问以及保存/加载索引。它可作为文档进入检索流程的实现参考。README中的云端文档产品是单独平台，不能把云服务等同于开源框架已经包含的能力。

本业务设计建议按以下方式接入：文档接入时同时维护事实ID与来源位置；在检索索引之外维护批准状态和有效区间；查询时先绑定可见范围；召回结果回到权威事实库验证；将`answer`判定输出交给模型表达；保存引用和人工审核记录。

上游提供检索组件，不自动提供本文的产品审批、客户权益或承诺边界。示例为独立标准库程序，没有复制上游代码，没有安装或运行LlamaIndex。来源记录保留精确SHA与学习范围，已有[MIT许可副本](../agent-case-studies/licenses/llama-index.txt)供核对。

## 10. 最小可运行例子

```bash
python knowledge/business-ai-cases/examples/sales_knowledge_demo.py
python knowledge/business-ai-cases/examples/test_sales_knowledge_demo.py
```

[源码](examples/sales_knowledge_demo.py)只依赖Python标准库。`CapabilityBook`验证记录状态、日期区间、重复ID和条件字段；`answer`返回产品、能力、查询日期、事实库版本、状态、记录ID、证据ID、缺失字段与不满足条件。它不生成随意文本，便于作为模型前的业务判定层。

`audience`是演示参数，不是真实认证机制。生产中该字段、事实库快照与查询日期应来自可信服务上下文，不能接受模型或外部调用者随意提交`internal`。本文也没有租户隔离；带客户合同的私有能力库需要额外按租户和合同授权。

2026-10-05在Python3.12.14实际运行[20项离线检查](examples/test_sales_knowledge_demo.py)，全部通过。覆盖支持、缺条件、不适用、规划、明确未支持、无证据、产品隔离、内部资料可见范围、版本切换日、历史查询、未来资料、草稿过滤、批准记录冲突、空证据和异常输入。[运行记录](examples/sales-knowledge-results.json)包含六种常见查询输出。[来源记录](examples/sales-knowledge-sources.json)说明出处与已验证范围。

检查只验证精确ID、合成事实与规则；不覆盖自然语言理解、Embedding召回、真实账号授权、来源有效性、模型润色正确性、CRM集成或线上收益。

## 11. 做业务验收时分别统计哪几件事

先整理真实已授权需求的人工答案，每题记录产品、客户条件、时点、预期状态与证据。评测集合至少包含“问法相似但产品不同”“老手册与当前版共存”“内部预览”“规划功能”“合同例外”“缺少客户信息”。题目中的参考答案不要传入待测模型。

分别统计事实检索召回、状态判定、适用条件完整率、引用正确率和不当承诺数。高总体答对率仍可能掩盖少数“把规划说成已上线”的错误；应单列高风险类别，并由业务方定义交付阈值。

上线试点可以先生成内部草稿，与原人工流程比较核查用时、退回修改次数和知识库缺失率。不要只统计生成文本耗时；销售仍需花很多时间纠错时，业务价值可能没有提升。本文没有测量任何真实节省比例。

## 12. 练习与下一步

给导出功能增加`deployment=cloud`条件：缺部署信息时应返回`needs_info`；私有化客户应返回`not_applicable`。再增加未来生效的批准版本，并结束旧版，检查切换日是否只命中一条记录。

进一步把引用ID接到真实可授权的来源服务，加入源文件撤回和版本变化后的重新核验。只有这一步落地并通过真实题集，才有依据讨论“知识库答复可靠”；本文完成的是可复跑的业务判定教学层。
