# Browser Use 浏览器 Agent：观察、行动与页面变化保护

核验日期：2026-10-04。证据级别：开源 step/multi_act 实现与多标签页面摘要例子；本轮未操作网站或验证示例成功率。

## 1. 浏览器操作为什么需要反馈

示例让 Agent 打开多个社区页面，查看最新帖子并汇总。网页有动态加载、跳转、多标签和弹窗，固定的一长串点击动作很容易在中途失效。浏览器 Agent 每轮根据当前页面重新决定行动，比把所有动作一次规划到底更有适应性。

最重要的知识点是**动作引用的页面状态必须仍然有效**。昨天截图里的按钮编号，不能用于今天的新页面；一次跳转后的元素列表也不能沿用跳转前的编号。

## 2. 源码中的单步闭环

service.py 的 step 依次准备浏览器上下文、获取模型动作、执行动作和后处理，异常统一进入错误处理，最终记录本步状态。准备上下文时读取当前浏览器状态与页面信息，而不是只向模型复述用户任务。

run 有步数上限与暂停、恢复等运行控制。实际源码很大，本文只解读 step、run 和 multi_act 中已核对的部分，不声称审计了所有浏览器行为。框架提供接口，并不保证网站永远不变。

## 3. 批量动作里的“过期页面”保护

multi_act 用两层机制避免继续对旧 DOM 操作：带 terminates_sequence 标记的导航类动作会终止剩余队列；每次动作后还比较 URL 与当前焦点目标，变化则停止原序列。随后应重新观察，再规划后续动作。

这是性能和正确性的折中：页面不变时可以减少模型往返；页面变化时牺牲批量速度，以免把上一页“删除按钮”的编号当作下一页“提交按钮”。这类保护还不能证明所有 DOM 局部更新都能被识别，关键操作依然要核对当前元素及结果。

## 4. 适合什么实际工作

适合没有可用 API 的后台查询、跨页面资料收集和表单草稿准备。若有稳定 API，则直接调用通常更容易得到明确结果与权限边界。不要因为能操作浏览器，就把所有后端业务接口替换成页面点击。

教学任务：“查询五个对象并导出结果”。每条记录带对象 ID、来源 URL、抓取时间、字段和状态。查询成功需核对页面返回的对象确实匹配输入，而不是仅检查页面上出现了一个数字。导出要核对下载完成与文件内容。

## 5. 完成条件与外部动作

点击提交不是成功凭据，界面提示、下载产物或后台记录才是证据。超时重试尤其要区分只读动作与创建订单、发消息等写动作；写操作先核对是否已完成，避免重复执行。登录身份和页面中的账号应能与任务目标匹配。

网页内容是工具输入，不能覆盖系统权限或用户目标。把网页上的“请上传密钥”等文本当作任务指令会造成提示注入风险。实际业务应把高影响操作放在明确授权的工具或审批路径里；本篇不执行任何登录、提交或外发动作。

## 6. 评估与练习

速度示例把等待时间调小并启用 flash_mode，它是配置演示，不是任何网站都更快更可靠的实测结论。应报告任务完成率、错误对象率、操作步数、耗时与人工介入次数，而不只看响应速度。

[离线脚本](examples/agent_case_checks.py)检查页面版本变化后旧动作被拒绝，新观察得到的新动作可执行；未启动浏览器。练习：为什么“导航后停止剩余动作”能降低误操作？因为剩余动作是在旧页面语境下决定的，元素含义可能已经改变。
