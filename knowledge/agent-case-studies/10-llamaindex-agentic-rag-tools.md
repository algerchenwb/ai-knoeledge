# LlamaIndex Agentic RAG：把不同资料库封装成检索工具

核验日期：2026-10-04。证据级别：官方两份年度报告查询与对比 Notebook；本轮未构建索引或调用模型。

## 1. 一个可追溯的跨文档案例

官方 Notebook 分别读取2021年的 Lyft 与 Uber 10-K 报告，为每家公司建立 VectorStoreIndex，持久化后创建 query engine。两份文档各包装为 QueryEngineTool，分别命名 lyft_10k 和 uber_10k。ReActAgent 可以回答单家公司问题，也可以调用两边资料回答增长对比问题。

这里的知识点是**工具可以是一个完整的检索与回答系统**。上层 Agent 选择去哪里问，下层检索工具在限定语料里找证据。与把所有文档直接塞进同一个提示相比，它提供了更清晰的来源边界。

## 2. Agentic RAG 多了什么

普通 RAG 常做一次检索后生成回答；Agentic RAG 可以根据结果继续检索、切换资料源、分解问题或比较答案。两份报告的工具描述包含公司和年份，模型据此决定调用哪个工具。

它仍依赖文档解析、切块、Embedding 与检索质量。上层 Agent 不会自动修好下层漏掉的表格或错误数字。代码把 similarity_top_k 设为3，意味着每次查询检索有限候选，不代表前三条一定覆盖全部相关证据。

## 3. 顺着源码读执行路径

先尝试 load_index_from_storage，失败后才加载 PDF 并构建索引；然后用 QueryEngineTool.from_defaults 添加名称和描述；创建 ReActAgent，把 Context 用于会话状态；agent.run 返回 handler，并可通过流式事件观察生成过程。

流式事件可以区分 AgentStream 与 ToolCallResult。业务审计更应保存工具名称、查询参数、来源及输出结果；流中生成的解释不是事实来源，也不应把自然语言推断过程当作成功证明。

## 4. 对业务知识库的迁移价值

教学改造：给“指标定义库”“接口能力库”“数据质量说明库”分别提供工具。用户问某区域客流为什么下降，先确认指标口径，再取得对应版本的数据质量说明，必要时调用受控查询 API 验证。最后回答把事实数据、指标解释和可能原因分别呈现。

工具名使用业务含义，内部可接 Qdrant、Neo4j 或普通检索服务。这个案例不要求把向量数据库、图关系或内部字段全部暴露给最终用户。模型可以知道可查询的业务能力，前端给出可读来源标题与版本。

## 5. 防止跨语料和跨版本混用

2021年的数据不能回答2026年的事实，某租户资料不能成为另一个租户的证据。工具描述只是路由提示，真正的语料过滤、权限和时间限制要由检索服务执行。持久化索引还需记录文档哈希、Embedding 版本和切块配置；仅因为目录存在就读旧索引，可能得到过期数据。

比较增长率时要核对报告期、币种、指标定义和基期。检索回答是文本，必要时将金额和口径解析成结构化字段，由确定性函数计算比例，避免二次总结引入算术错误。

## 6. 评估与版本说明

除最终答对率，还检查工具选择正确率、检索覆盖、引用支持和跨库泄漏。加入只属于一家公司的问题、同时需要两份报告的问题，以及语料没有覆盖的年份，观察是否明确拒绝外推。

2026-10-04 README 写明公司当前重点已转向文档解析与提取，OSS 框架仍作为开放工具可用。本篇讨论固定快照里的框架案例，不把 LlamaParse 等商业服务都归为开源实现。

[离线脚本](examples/agent_case_checks.py)检查两份虚构资料按 company/year/tenant 范围检索，不覆盖时返回空，未运行 LlamaIndex。练习：为什么给检索工具取“所有资料”这样的名字会增加误用？因为模型没有明确的来源选择依据，开发者也难以把权限与版本边界表达清楚。
