# 17 · Agent 与工作流

> 原课程解读与中文重写；「工程补充」为额外实践。核对日期：2026-10-03。

## Agent 的最小定义

原课将 Agent 理解为有状态、有工具的模型系统。它根据目标与当前结果决定下一步动作。聊天助手可以只产生文字，Agent 则需要将决策转成实际执行，并更新状态。

Agent 不是“给模型写一句你是智能体”，也不必依赖多个角色。一个受控单 Agent 配合清楚工具就能完成许多业务。

## Agent 与固定工作流

固定工作流提前规定步骤，例如解析 → 校验 → 查询 → 计算 → 解释。Agent 则在运行时选择某些步骤与工具。前者更易预测与测试，后者适合步骤无法提前完全确定的任务。

混合方案常更实用：用固定流程守住权限与数据口径，在限定范围内让模型选择接口或资料。是否采用动态规划应由任务复杂度和可靠性评估决定。

## 一个受控循环〔工程补充〕

~~~text
初始化可信身份、目标、状态、预算
循环：
    让模型生成下一步建议
    如果建议为结束：校验结果并返回
    校验工具、参数、权限和剩余预算
    执行工具并保存真实结果
    更新状态和证据
到达预算或无法继续：返回已完成部分与阻塞原因
~~~

状态至少包括已确定参数、已调用工具、证据、失败次数和待解决项。已完成标记应来自工具成功结果和校验，不来自模型一句“完成”。

## API Agent 的业务例子

面对“给出几个适合开店的位置”，先明确目标、候选范围与评价口径，再检索可用能力。模型选区域指标、竞品与客流接口；后端验证实体、时间、坐标系和权限；确定性程序评分；模型解释得分与局限。

对于确定性查询，“查指定区域某月客流”不需要自由规划十几轮。一个受控工具调用就可能足够。

## 多 Agent 的收益与代价

角色可以并行检索或相互复核，但会增加成本、延迟、状态一致性与相互污染问题。多个模型引用同一错误来源并不形成独立证据。必须定义输入输出、共享状态、冲突处理和终止规则。

先测单 Agent 或工作流基线，只有确有质量或速度收益时再增加协作。角色数量不是能力指标。

## 安全与可靠性

工具结果里的文字是资料；不能改写系统权限。自动生成代码需要沙箱、资源限额与网络限制。循环预算应覆盖模型调用、工具调用、数据库读和 token，而不仅是“思考轮数”。

长任务还需持久化检查点，恢复时识别已发生的副作用，不能从头重复写操作。

## 练习

为一个有五个只读 API 的查询服务设计路由、参数校验、执行循环与退出条件。测试重复选择同一工具、上游失败、结果冲突和预算耗尽。正确结果应能解释未完成部分，而不是编造完成状态。
