# 第18课深化：微调数据、训练目标与适配器

> 对应 [第18课概览](../18-fine-tuning.md)；上游快照 `d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8`，核对日期 2026-10-04。
> 本文解释机制并提供工程设计；没有实际启动云端训练或 GPU 实验。

## 1. 微调应该解决哪类问题

微调通过优化参数改变模型的行为分布。它适合反复出现、可提供优质示例的任务，例如特定输出风格、领域术语和结构化提取。它不能保证记住每条资料，也不能替代实时数据库、权限检查或可靠的事实检索。

先建立提示词与 RAG 基线，再判断失败原因：

| 失败 | 优先排查 | 微调的潜在价值 |
|---|---|---|
| 不知道昨天发布的制度 | 检索和文档更新 | 通常不宜靠重训维护事实 |
| 已有证据但格式不稳定 | Schema、提示、输出验证 | 学习稳定的响应模式 |
| 缺少专业术语理解 | 术语检索和任务数据 | 适配领域表达与任务 |
| 工具调用越权 | 执行器权限检查 | 不能提供权限保证 |
| 模型无法处理目标模态 | 架构和 processor | 普通文本微调不能凭空增加视觉接口 |

“训练损失下降”表示优化目标在训练数据上更好，不等于用户任务成功率更高。

## 2. 区分训练目标

- **继续预训练**：在文本语料上继续学习语言建模目标，可用于领域适配。并不是简单更换几个超参数。
- **监督微调（SFT）**：用输入与期望输出示例教模型完成任务或响应对话。
- **偏好优化**：利用回答之间的偏好信号，优化响应选择；不同算法有不同目标与假设。
- **全参数微调**：更新大量或全部基座参数，训练资源和保存成本通常较大。
- **参数高效微调（PEFT）**：仅训练部分新增或选定参数，是参数更新方式，不是独立的业务任务。

数据形式、优化目标和更新哪些参数是三个维度。SFT 可以用全参数方式，也可以使用 LoRA。

## 3. LoRA 为什么参数少

以一个形状为 m×n 的线性权重矩阵 W 为例，LoRA 冻结 W，用两个较小矩阵表达更新：

```text
W_effective = W + scale × B × A
A: r × n
B: m × r
新增可训练参数数 = r × (m + n)
原矩阵参数数 = m × n
```

这里 r 是设定的低秩维度，scale 表示实现中的缩放。示例 m=n=4096、r=8：原矩阵有 16,777,216 个参数，两个适配矩阵共 65,536 个参数，即该矩阵的 1/256。这个比例仅针对这一矩阵；整个模型的比例还取决于应用哪些层、是否训练偏置和额外模块。

[LoRA 原论文](https://arxiv.org/abs/2106.09685)提出冻结预训练权重并训练低秩更新。参数少不等于没有基座加载成本，也不表示训练过程不保存梯度、激活或优化器状态。

**QLoRA 的核心区分**：量化冻结的基座，并训练 LoRA 适配参数；不要理解成“把所有权重都以 4 bit 直接训练”。可参考 [Hugging Face PEFT 量化文档](https://huggingface.co/docs/peft/developer_guides/quantization)。实际支持的量化后端、目标模块与数据类型要按锁定版本验证。

## 4. 一个好样本应该有什么

业务目标：“从客户来信提取订单号；缺失时返回 null；不能编造。”

```json
{
  "record_id": "sample-001",
  "group_id": "ticket-042",
  "messages": [
    {"role": "system", "content": "提取订单号；缺失返回 null。"},
    {"role": "user", "content": "我想查询 AB-1234 的物流。"},
    {"role": "assistant", "content": "{\"order_id\":\"AB-1234\"}"}
  ]
}
```

这是知识库自定义教学格式，`record_id` 和 `group_id` 用于检查，不代表任一云平台直接接受它们。导出训练文件时应按平台或训练器支持的 Schema 转换。

数据应同时包含：有答案、无答案、多编号、歧义、干扰文本、信息冲突、需要拒答和格式异常。只收集成功且简单的例子，会让模型学会“每次都填一个值”。

人工审查应确认期望输出本身正确。错误标签越一致，模型越容易稳定地学错。

## 5. 划分数据时防止泄漏

随机按“行”切分并不总是安全。一份合同的十个片段、同一工单的改写、同一模板的轻微变体可能出现在不同集合。模型看到近似答案后，测试成绩会虚高。

工程补充：

1. 给同源文档、客户工单或实体赋稳定 group_id。
2. 按组划分 train、validation、test；必要时按时间划分。
3. 检查完全相同或标准化后相同的输入跨集合重复。
4. 再检查近似重复、模板泄漏和标签来源污染。
5. test 用于最终评估，不反复用于选择超参数。

精确重复检查只能发现精确或规则标准化后的重复，不能声称识别了所有语义相似内容。

## 6. 模板、截断与 loss mask

训练时和推理时应使用兼容的角色模板和特殊 token。截断可能删掉答案、证据或关键约束。统计 token 长度并检查最长样本，比仅看 JSON 文件有效更可靠。

对于“只训练助手答案”的配置，loss mask 控制哪些 token 参与损失；有些配置也训练全部文本。必须检查训练器实际行为，不能因为数据中写了 role=assistant 就推断输入部分自动被屏蔽。

若推理要求 JSON，训练目标应是一致的 JSON，而不是同时混入解释段落、Markdown 围栏和不合法字段。输出验证仍需保留，因为模型学到的是概率行为。

## 7. 如何看训练结果

| 观察 | 可能含义 | 下一步 |
|---|---|---|
| 训练损失降，验证变差 | 过拟合或集合分布不同 | 查数据与训练强度 |
| 格式更好，内容更差 | 模型学习格式却损失任务能力 | 分离格式与事实指标 |
| 训练集效果高，测试低 | 泄漏、分布差异或记忆 | 查分组与新样本 |
| 专项提升，通用能力退化 | 适配影响原有任务 | 加入回归集 |
| 量化后工具参数变差 | 部署精度影响表现 | 测部署产物而非训练产物 |

保留相同基座、相同检索输入和相同生成设置的对照。记录训练数据版本、seed、超参数、基座 revision、adapter 配置、训练日志与部署精度。seed 有助复现，但不保证不同硬件和运行时结果完全相同。

## 8. 交付的是一套兼容关系

adapter 本身通常不包含完整基座。交付时至少说明：适配器对应哪个基座版本、哪个 tokenizer、什么任务、哪些目标模块、如何加载与评估。合并 adapter 后也要重新测试保存与加载结果；能合并不等于适用于所有量化或运行时组合。

源课程提到的模型可用范围、云服务部署限制、保留时间和费用具有平台与版本差异。不要将课程中的数值作为普遍规则；本文不据此承诺训练成本或部署资格。

## 9. 实践与自测

先用几十条经过审查的样本做数据管线试验，确认角色模板、标签与评估读取正确，再决定扩大训练。这个规模用于发现管线问题，不是效果充分性的保证。

请解释：

- RAG 更新事实与微调改变行为的区别。
- 同一文档的不同片段为什么应优先按组切分。
- 为什么 LoRA 仍需要加载基座。
- 为什么只看训练 loss 不能验收模型。

答案方向：事实来源与参数行为不同；同源信息会泄漏；adapter 是基座上的更新；最终质量需要独立测试与部署回归。
