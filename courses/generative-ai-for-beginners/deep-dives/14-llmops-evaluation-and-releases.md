# 14 · LLMOps深化：评测集、版本、观测、发布与回滚

> 第14课深入解读，核对日期：2026-10-04。「工程补充」为原创交付方法。课程提到的产品与界面按固定快照理解，本文不比较当前平台功能与价格。

## 1. LLMOps不是只收集模型日志

课程把生命周期分为探索、构建与增强、运营，并以管理贯穿各阶段。它不是一次性直线：部署后的问题需要回到资料、提示词、检索和工具设计。

LLMOps可以理解为“让生成式AI应用可测量、可维护地交付”。它继承普通软件与MLOps的许多实践，同时增加生成行为、检索资料和模型服务变化的管理。

应用开发者即使不训练模型，也要管理自己控制的提示词、数据、工具、状态和版本。没有微调任务不意味着没有LLMOps工作。

## 2. 从业务假设开始

“模型能回答问题”过于宽泛。可验证的假设应该包含任务、输入范围与成功条件。

原创例子：

```text
对于已确认区域、月份和人群的请求，
应用能从指定业务接口取得聚合指标，
并在保留统计口径与来源的前提下生成中文解释；
无权限、无数据、口径冲突时不得编造结果。
```

这个定义让接口、权限、数据与生成都进入验收，而不是只看文案。

探索阶段先用小样本验证任务是否适合模型；构建阶段增加数据与边界；运营阶段观察真实请求和变化。每一阶段的失败都应能定位到具体环节。

## 3. 一个结果由哪些版本共同决定

| 版本或资产 | 改变可能带来的影响 |
| --- | --- |
| 模型与部署配置 | 指令遵循、工具选择、延迟 |
| Prompt模板和示例 | 输出格式与缺项处理 |
| 工具目录与Schema | 路由、参数、调用能力 |
| 业务API与数据口径 | 数字含义和可比性 |
| 知识资料快照 | 证据内容 |
| Embedding与切块规则 | 候选召回 |
| 索引、重排与阈值 | 排名与无答案行为 |
| 会话状态处理 | 条件继承与多轮结果 |

只记录“模型版本”无法重现完整应用。至少为一次发布建立版本清单，并为每个请求记录实际使用的版本。

模型服务可能只暴露部署别名或部分版本信息，应记录能获得的信息并说明复现限制，不假装可以固定所有底层因素。

## 4. 评测集应该长什么样

一条评测样本可以包含用户请求、必要历史、可信身份、可用资料、预期动作、允许结果与禁止行为。

例子：

```json
{
  "case_id": "example-no-data",
  "request": "查询示例区域2026年9月工作人群",
  "tool_fixture": {"status": "no_data", "data": null},
  "expected": {
    "answer_status": "no_data",
    "must_not_claim_population_zero": true,
    "must_not_invent_statistics": true
  }
}
```

这里是教学数据。不是要求所有系统使用同一格式，而是强调标签应与任务有关。

评测不能只有“标准答案字符串”。同义表达可以合格，但使用错误月份或编造数值必须失败。对工具和结构化字段，确定性校验通常比自由文本评分更可靠。

## 5. 构造样本时避免泄漏与偏差

需要同时包含：

- 高频正常请求。
- 缺字段、歧义、冲突和无答案。
- 工具错误、超时、部分失败。
- 权限边界与恶意资料。
- 多轮修改与重发。
- 长输入、中文缩写与业务术语。

提示词中的Few-shot示例不能又当作独立测试结果来证明泛化。调参集与最终验收集应区分。

真实日志可以帮助补充样本，但要先处理敏感信息、明确预期行为并经复核。不能把用户点赞视为事实正确标签。

按任务切片报告结果。多数普通样本表现好，可能掩盖少数但关键的权限失败。

## 6. 课程的五类指标怎么落地

课程强调质量、伤害、依据、成本与延迟。可映射为：

| 维度 | 应用指标 | 典型误区 |
| --- | --- | --- |
| 质量 | 任务完成、参数正确、格式有效 | 把文笔评分当总质量 |
| 伤害与边界 | 越权阻止、敏感暴露、错误动作 | 只看最终拒绝文字 |
| 依据 | 关键陈述是否由输入证据支持 | 有引用就认为有依据 |
| 成本 | 每次有效任务的总消耗 | 忽略失败与重试 |
| 延迟 | 首段、完整任务、尾部耗时 | 只看平均值 |

“Grounded”和“真实”也不完全相同：回答可以忠实引用一份错误文档。既要检查支持关系，也要检查来源与有效性。

平均延迟会掩盖少量很慢的请求。可以按任务类型查看分位数，并注明样本规模和统计窗口。

## 7. 检索、工具与生成分层评测

把完整系统拆成可检查的环节：

1. 查询理解：条件是否正确。
2. 检索：是否找到可用资料。
3. 请求组装：资料是否真的送入模型。
4. 工具：实际调用是否正确、合法。
5. 生成：是否忠实解释结果。
6. 展示：状态和来源是否准确。

RAG Notebook里的证据传递错误说明第三层尤其重要。模型可能凭预训练答对问题，使“最终答案正确”掩盖资料根本没传入的缺陷。

只有端到端测试不够，只有组件测试也不够。两者结合才能区分局部成功与整条链路成功。

## 8. 模型评分器怎么用

模型评分器可辅助审查相关性、表达与证据关系，但它也可能受偏好、位置、资料中指令和自身知识影响。

应提供明确标准，用人工标注样本校准，并记录评分器版本。对于数值一致、字段类型、权限与实际副作用，优先使用程序与执行记录。

不能用同一个被评测模型自述“我回答准确”来替代测量。评分器给出的0.9也不自动成为经校准的正确概率。

高风险错误由独立规则或审核决定，不能被其他维度高分抵消。

## 9. 发布条件不应只看一个平均分

原创例子：候选版本的普通任务正确率从90%提高到95%，但发生了一次越权读取。不能因为平均质量提高就认为可以上线。

可以设置两个层次：

- **必须通过的约束**：权限、数据泄漏、非法工具、数值契约。
- **比较性指标**：正常任务成功、延迟、成本、误拒绝。

门槛应来自业务需求和风险，而不是照搬一个统一百分比。固定测试通过也不意味着绝对无风险，只代表对已覆盖样本满足验收。

保存基线与候选在同一评测集、相同工具数据和明确配置下的结果。模型随机性较高时，考虑重复运行并报告波动。

## 10. 可回滚发布清单〔工程补充〕

一次发布可以包含：

```text
release_id
application_commit
prompt_version
tool_catalog_version
knowledge_snapshot
embedding_config
index_version
model_deployment_config
evaluation_dataset_version
evaluation_report
rollback_target
```

这份清单用于维护，不需要全部展示给业务用户。

Prompt和索引版本不匹配时，单独回滚Prompt可能不够。旧Schema对应旧工具实现时，也不能只切模型。需要明确哪些资产必须一起切换。

数据写入和外部动作未必能靠软件回滚撤销。对副作用应设计幂等、执行记录和必要补偿，而不是把“回滚代码”当成撤销所有影响。

## 11. 灰度、影子流量与副作用

灰度可以限制影响范围，并比较真实任务表现。影子流量则把请求复制给候选系统观察结果。

对只读生成任务，影子流量仍要考虑资料权限和费用。对发信、支付或修改记录，不能让影子系统再真实执行一遍。应该使用只读或模拟执行端，并检查候选提出的动作。

用户取消、重试与会话状态也需要一致设计。否则候选系统看到的状态与基线不同，比较结果会失真。

## 12. Trace如何帮助定位

一次区域画像请求可记录需求解析、实体解析、数据调用、结果校验和生成等子阶段。

建议记录request_id、父子阶段关系、输入输出大小、状态、耗时和版本。日志中的原始内容需要按敏感性限制，不能为了调试无条件采集全部资料。

如果“模型调用慢”，需要确认是排队、资料读取、工具重试、模型生成还是客户端传输慢。只记录一个总时长不够。

异常告警应关联业务影响，比如错误率上升、工具失败、无依据数值、预算耗尽或索引更新异常，不只是CPU。

## 13. 线上反馈到离线回归

故障处理建议形成闭环：

1. 定位请求与版本。
2. 复现资料、工具返回和状态。
3. 确认根因与修复层次。
4. 加入去敏的回归样本。
5. 比较基线与修复结果。
6. 发布后观察是否引入新失败。

不要为每个问题盲目追加一条Prompt。错误可能发生在查询、口径、索引或请求组装，修复应落在实际责任层。

## 14. 自查

- 更换文档需要回归吗？需要，资料变化会影响答案。
- 没训练模型就不需要LLMOps吗？仍需要管理应用资产。
- 模型评分器能证明权限安全吗？不能，需独立验证实际访问。
- 回滚模型能撤销已发送邮件吗？不能，副作用单独处理。
