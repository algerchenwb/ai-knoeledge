# 05 · 高级提示词深化：示例、分解、自检与确定性校验

> 对原课程的深入解读与原创业务案例。核对日期：2026-10-03。本文将课程技巧与工程限制分开说明；技巧是否有效应通过实际任务评测。

## 1. 先判断错误来自哪里

“模型答错了”不是足够具体的诊断。可能是问题没有说明、知识材料不存在、任务太复杂、输出格式不一致，也可能是程序缺乏校验。不同原因需要不同处理。

| 失败现象 | 优先尝试 | 必须检查 |
| --- | --- | --- |
| 同一业务词理解不一致 | 术语定义与 Few-shot 示例 | 示例是否代表真实口径 |
| 漏掉步骤 | 拆分为有输入输出的子任务 | 中间结果是否正确 |
| 没有资料却给出结论 | 证据与缺项规则 | 来源和引用是否真实 |
| 多个条件不能同时满足 | 显式约束与程序检查 | 是否应该返回无解 |
| 自检后仍然错 | 引入独立证据或计算器 | 不能只靠再问一遍 |

高级提示词不是越长越高级，而是使错误更容易定位、结果更容易验证。

## 2. Zero-shot 与 Few-shot

Zero-shot 是直接给任务，不提供输入输出示范。例如“将需求分类为客流、画像、围栏、其他”。它仍可以包含规则和背景；“零样本”不等于没有上下文。

Few-shot 是在当前输入里提供少量任务示例。它影响这次生成，并不等于重新训练或修改模型参数。

原创示例：

```text
任务：按需求的主要目标分类，只返回分类名称。

例1：查询 A 商场 9 月每日到访人数 → 客流
例2：查询 A 商场的年龄分布 → 画像
例3：导出 A 商场边界 GeoJSON → 围栏
例4：查询某人的手机号和住址 → 不支持

新需求：比较 A 商场和 B 商场最近一月的客群重叠。
```

这里存在一个刻意保留的问题：标签表没有“客群重叠”。合理做法是先定义分类规则，明确归入哪个标签或是否要新增标签，而不是让模型凭相似度决定产品路由。

示例设计应覆盖边界、缺项、冲突和拒绝场景。所有例子都成功，会让模型更容易忽略“不支持”和“需要补充”的合法输出。

工程上还要将示例集与评测集分开。把某请求直接用作示例后，再拿同一请求验证，不能证明对新请求有效。

## 3. Chain-of-thought：提供可核查的步骤示范

原课程用苹果数量的例子说明：给出相似问题的计算步骤，可能帮助模型处理新的多步问题。关键价值是把任务结构表达清楚，而不是要求输出越长越好。

业务应用可以要求模型输出**简短依据、公式和结果**，不必索取内部思维过程。例如：

```text
依据字段说明给出口径解释。
计算由程序完成；回答须列出公式、输入数值、最终值及缺项。
不要把未提供的事实写进依据。
```

假设虚构数据中“近90天到访过4S店的去重人数”为 240、“近90天AOI去重客流”为 1200，程序计算 240 / 1200 = 20%。模型可以解释这个比例，但必须先确认：

- 分子人群属于分母的人群集合；
- 分子和分母都是同一时间窗口；
- 都按同一标识去重；
- 4S店分类定义一致。

若分母实际为累计到访人次，240 / 1200 就不能解释为“触达人数占比”。漂亮的推导无法弥补口径错误。

## 4. Generated knowledge：背景知识不一定是证据

原课程在这个标题下展示了把公司商品数据填入模板的做法。需要区分两件事：

1. **注入已有知识**：公司 API、数据库或文档提供资料。
2. **生成背景知识**：先让模型写出相关知识，再用它辅助后续回答。

第一种可以有可追溯来源，第二种仍然可能包含编造。模型生成的一段说明，不能因为再次传回模型就变成经过验证的事实。

例如让模型先解释“驻留人群”再生成 SQL，如果第一步把“工作人群”与“常驻人群”混同，后续 SQL 会沿着错误定义执行。应由业务口径文档提供定义，再让模型映射字段。

### 原课程保险例子的实际限制

课程先给出预算与产品列表，再优化提示词来限制选择。值得注意的是，优化后的需求删减了原来的覆盖要求，所以“买一个便宜产品”不等于解决原始的全部保障需求。

在真实系统中要分别判断“合法”“预算内”“覆盖需求”。如果同时满足所有条件没有方案，应返回无可行方案，或明确说明哪些条件需要放宽。不能偷偷删掉一个要求，再报告任务成功。

## 5. Least-to-most：把复杂任务拆成依赖明确的小任务

原课程强调分解问题，从较简单的步骤逐渐完成复杂任务。下面是区域分析的工程拆分：

| 子任务 | 输入 | 输出 | 校验 |
| --- | --- | --- | --- |
| 解析需求 | 用户原话与日期基准 | 区域、时间、人群、指标 | 字段类型与缺项 |
| 解析实体 | 区域名称、候选列表 | 唯一区域 ID 或歧义 | 不能凭空造 ID |
| 获取资料 | 已校验的参数 | 指标值与来源 | 权限、时间、完整性 |
| 计算变化 | 已校验数值 | 差值与比例 | 分母、单位、去重口径 |
| 生成解释 | 数据和计算结果 | 业务说明 | 不增加无依据原因 |

拆分的收益是发现错误来源，代价是增加调用、延迟与中间状态。不是每一格都要调用一次模型：实体查询、权限判断和数值计算通常应该由程序完成。

下游必须使用通过校验的上游结果。不能上一步已经发现区域歧义，下一步仍然取第一个候选查询。

## 6. Self-refine：带验收标准的自检

原课程流程是初稿、批评、修订。有效的批评需要标准，例如：

```text
审查下面的指标解释：
- 每个数值能否对应到输入字段？
- 月份和人群类型是否一致？
- 是否把相关性说成因果关系？
- 分母为零时是否仍生成比例？
仅列出具体问题和对应片段。没有问题可返回空列表。
```

模型可能指出错误，也可能给正确答案添加不必要修改。自检不是独立证明，因为生成者和审查者可能共享同一种误解。

工程建议：先做确定性检查，再用模型审查难以规则化的表达。最多设定少量修订轮数，保留前后版本，避免无限循环。只因评审模型给出高分，不应自动跳过业务校验。

## 7. Maieutic prompting：追问解释中的矛盾

原课程介绍通过追问各个部分，寻找不一致。例子：

- 初答：8月与9月可直接比较。
- 追问：两个月的地理边界是否相同？
- 补充：9月扩大了边界。
- 修正：总量变化混合了范围变化，不能简单归因于经营变化。

这有助于暴露隐含假设。但“前后没有矛盾”只能说明内部一致，不能证明事实正确。一个虚构故事也可以非常一致。

## 8. Temperature 的正确心智模型

在支持温度采样的模型中，可以用下面公式理解影响：

```math
p_i = \frac{\exp(z_i/T)}{\sum_j \exp(z_j/T)}
```

其中 z_i 是候选 Token 的分数，T 是温度。较低的正温度让高分候选更突出，较高温度使概率更平缓。这个公式用于解释机制；不能直接把 T=0 代入，零温度通常由服务按其实现处理。

原课把范围和默认值写成固定数字，不能泛化到所有模型和 API。不同模型可能有不同范围、默认值，甚至不允许调整温度。

低温度不保证事实正确，也不保证逐字一致。模型版本、后端实现和其他采样设置变化都可能改变结果。业务稳定性更依赖固定契约、资料、校验与回归测试。

## 9. 可复现的小实验〔工程补充〕

准备 12 条区域指标请求：4 条正常、4 条缺项、4 条口径冲突。对比三组配置：

- A：只给任务。
- B：任务加字段规则。
- C：任务、字段规则加边界示例。

记录参数有效率、缺项识别率、错误补全率、延迟和 Token 用量。每条可重复运行若干次，观察波动，避免单次成功带来的错觉。示例不得与这 12 条请求相同。

如果 C 的 JSON 有效率提高但缺项识别变差，应检查示例是否让模型倾向于补齐所有字段。整体平均分可能掩盖严重错误，需要按失败类型分析。

## 10. 自查答案

- Few-shot 会更新模型权重吗？不会，它是在当前上下文里提供示范。
- 同一个模型批评自己能证明正确吗？不能，只是一个辅助检查渠道。
- 没有预算内的完整方案怎么办？返回无解并指出冲突条件。
- 为什么数据查询要先处理实体歧义？否则后续解释再流畅，也可能回答了错误地点。
