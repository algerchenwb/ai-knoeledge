# 第02课深化：模型分类、对照实验与选型

> 对应 [模型选择概览](../02-exploring-and-comparing-different-llms.md)。上游快照 d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8；核对日期 2026-10-04。
> 本文提供评测方法，不提供实时排行榜、价格或当前型号推荐。

## 1. 先定义工作，再选择模型

“哪个模型最好”缺少任务条件。一个模型可能代码生成强，但中文实体提取或工具参数稳定性不满足业务要求。选型应先写出：输入模态、输出契约、语言、可用证据、时延、权限、预算和失败时处理方式。

例如 API Agent 需要的不只是会回答中文，还包括识别正确接口、补齐必需参数、拒绝越权和在数据缺失时不编造结果。最终成功率由模型与执行器共同决定。

## 2. 分类有多个维度

| 维度 | 例子 | 能回答的问题 |
|---|---|---|
| 任务 | embedding、文本生成、图像生成、语音识别 | 选的是不是正确接口 |
| 模态 | 文本、视觉、音频或组合 | 输入是否支持 |
| 架构 | encoder、decoder、encoder-decoder | 训练与信息流的基础形态 |
| 适配 | base、instruct、特定任务版本 | 是否适合指令与对话 |
| 开放程度 | 托管闭源、开放权重、更多训练资产开放 | 可否自部署与修改 |
| 服务方式 | 云端API、自部署、边缘设备 | 运维与数据边界 |
| 部署精度 | 浮点、量化 | 资源与质量取舍 |

这些不是互斥菜单。一个开放权重的 decoder 指令模型可以通过云端 API 提供服务，也可以本地运行量化版本。

Foundation model 是可适配多种下游任务的基础模型概念，不仅包含语言模型。不能用“参数必须超过某个固定值”给所有基础模型划边界。

## 3. 架构类比的边界

Encoder-only 模型常用于文本表征、分类等；decoder-only 模型常用于自回归生成；encoder-decoder 通过编码输入、解码输出适合许多序列转换任务。课程中“创作者和审阅者”的类比有助入门，但不能当成能力限制：decoder 也可以分类，encoder 表征也可以参与更复杂系统。

架构不是完整质量预测器。数据、训练目标、适配、推理实现和任务分布都影响表现。

## 4. 模型与服务是两层

模型是权重、架构及配套资产。服务将模型包装成可调用能力，并提供认证、计量、配额、响应协议、部署与监控。

相同模型在不同服务中，可能有不同上下文限制、模板、工具调用格式、过滤策略、延迟和版本更新规则。服务支持“工具调用字段”与模型能正确选工具，也要分开评估。

某平台 catalog 能展示模型，不表示你的区域和账户支持部署、微调或某种计费方式。课程中的平台截图和家族清单只是快照。

## 5. 先做硬约束过滤

工程补充的选型顺序：

1. 排除不支持目标模态的型号。
2. 排除许可、数据处理边界或区域条件不满足要求的路径。
3. 排除设备资源或必需上下文不满足要求的部署。
4. 确认 SDK、输出格式与工具协议可集成。
5. 再比较任务质量、时延和成功任务成本。

硬约束不能被平均分掩盖。质量再高，若无法按要求部署，也不能进入最终候选。一个未经验证的“可能支持”应标为待核对，而不是通过。

## 6. 构建有代表性的测试集

从真实任务分布中采样并脱敏，覆盖常见请求和高影响边界。每条定义允许的输入、期望要点、必须拒答的情况、输出格式和评分标准。

API Agent 可以分成以下类别：

| 类别 | 检查重点 |
|---|---|
| 明确单接口问题 | 工具名称与必填参数 |
| 多接口组合 | 依赖顺序、共享条件 |
| 缺月份或区域 | 是否补足信息或明确失败 |
| 名称歧义 | 不把相似对象误当同一个 |
| 无数据 | 返回真实空状态 |
| 权限不足 | 不尝试扩大授权 |
| 工具错误 | 有限恢复与正确失败说明 |
| 恶意资料 | 不把内容变成执行权限 |

训练或调提示用的开发集与最终测试集分开。不能对每个测试错误改提示，然后继续把这个测试集报告成完全未见的评估。

## 7. 对照实验怎样公平

固定输入、证据、工具定义、输出预算与评价规则，记录模型具体版本和采样设置。对同一批样本做成对比较，保留每条差异。

一次响应无法支持稳定结论。对于有随机性或外部服务波动的指标，可以重复测量并报告分布。人工评价应尽可能隐藏模型名称，先制定标准，再评审输出。

| 指标 | 定义例子 | 容易混淆的地方 |
|---|---|---|
| 格式通过率 | 可解析且满足契约的比例 | 合法格式不等于内容正确 |
| 任务成功率 | 全部关键条件满足 | 不要只判断语言流畅 |
| 工具正确率 | 工具与参数都正确 | 仅工具名正确不够 |
| 证据支持率 | 结论可由允许证据支持 | 引用存在不等于引用正确 |
| p50/p95时延 | 中位数与尾部响应时间 | 样本太少时不稳定 |
| 每成功任务成本 | 总任务成本/成功任务数 | 忽略重试会低估 |

如果零个任务成功，每成功任务成本没有有限的有效值，应明确未达到可用条件。不要通过只统计成功请求的消费来隐藏失败成本。

## 8. 别把问题都归到模型

- 找不到证据：查索引、数据更新与检索。
- 找到了却未发送：查实际请求 payload。
- 发送了但被截断：查 token 预算与模板。
- 工具执行失败：查接口、授权、参数和超时。
- 输出解释错误：查模型与事实核验。
- 随版本升级突然退化：查模型、SDK和模板变更记录。

改变一层后，重跑受影响的验证。否则一次换模型可能同时改变模板和输出限制，难以知道哪项起作用。

## 9. 提示、RAG、工具与微调如何配合

提示定义任务，RAG 提供资料，工具访问实时业务事实或执行动作，微调改变稳定行为。这些方法可以组合。

课程把“模型只知道训练数据”作为入门说明；实际推理也可以使用用户提供的上下文与工具结果。更准确的表述是：参数中的知识不会自动实时更新，外部资料必须通过应用提供或工具获取。

先用最简单、可验证的基线建立失败分类，再决定是否增加检索、工具或训练。不要把“成本更低”作为提示工程或小模型在任何任务上的必然结论。

## 10. 练习

建立两个候选模型的结果表，列出每条任务成功与失败原因，另外保存时延、总成本、服务版本和硬约束核对结果。最后写三句话：选择理由、未解决限制、回滚触发条件。

自测：为什么一个总分更高的模型可能仍不入选？因为硬约束不满足，或关键任务、尾部时延、成本与权限边界不达标。
