# 第20课深化：用 Mistral 案例读懂 RAG、性能与 tokenizer

> 对应 [第20课概览](../20-mistral.md)。上游快照 d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8；核对日期 2026-10-04。
> Large 2（2407）、Small、NeMo 是课程快照案例，不是当前型号推荐。本文没有执行云端模型或 FAISS 实验。

## 1. 这一课的价值不在背型号

课程把三种模型放到 RAG、代码生成和 tokenizer 对比场景中。学习目标应是：将模型特性转成应用实验，而不是记住“某家族永远便宜或快速”。

同一家族中的不同版本可能改变许可、模态、上下文、工具协议和资源要求。“Large”“Small”是产品命名的一部分，不能代替具体模型标识和版本。

源课程提到免费可用、价格降幅以及固定几秒的时延差异。它们依服务、账户、版本与测试条件变化，本文不将这些数字作为当前承诺。latest 别名也不适合要求稳定复现的实验。

## 2. RAG 代码逐步看

| 原课步骤 | 实际作用 | 要额外确认 |
|---|---|---|
| HTTP下载文章 | 获取外部资料 | 超时、状态码、来源与内容类型 |
| 按2048字符切块 | 将字符串分段 | 字符不是token，可能切断语义 |
| Cohere生成embedding | 文档转成向量 | 配置、维度、输入类型和返回顺序 |
| FAISS IndexFlatL2 | 精确L2检索 | 数组类型、维度、索引映射 |
| 对问题生成向量 | 查询编码 | 必须与文档嵌入空间兼容 |
| 检索k=2 | 取近邻 | 有效ID、空库、相关性 |
| 拼接检索文本与问题 | 提供生成证据 | 来源、权限、预算和指令边界 |
| 模型生成答案 | 使用证据回答 | 支持性与引用核验 |

与第15课的某些原样例不同，第20课明确把 retrieved_chunks 放入实际发送的 prompt；这是需要肯定的链路事实。但证据进入请求，只证明资料传递，不能证明答案正确。

## 3. 下载和切块的隐患

requests.get 未在原片段中配置 timeout 或调用 raise_for_status。返回错误页时，response.text 仍可能是字符串，后续程序就会索引一份错误页面。

工程补充：限制下载大小，验证响应状态与内容，保存来源和版本。抓取成功后检查有效文本，避免空字符串继续进入嵌入接口。

原课按字符直接切段，没有 overlap、章节信息或来源位置。适合解释原理；真实文档可按标题、段落和 token 预算设计切块，并用检索评测选择策略。overlap 不是越大越好，会增加重复、存储和上下文占用。

## 4. 向量与距离的边界

FAISS 的 [入门说明](https://github.com/facebookresearch/faiss/wiki/Getting-started)要求明确矩阵维度与 float32 数据；[IndexFlatL2 文档](https://faiss.ai/cpp_api/struct/structfaiss_1_1IndexFlatL2.html)说明其搜索接口。工程中应显式准备形状为（数量，维度）的连续数组，验证有限值、维度与返回数量。

不要把 L2 距离当成“越大越相似”的分数。对于单位归一化向量：

```text
squared_L2(x, y) = 2 - 2 × cosine(x, y)
```

这是单位向量前提下的数学关系；未归一化时不能直接转换。是否归一化以及使用何种距离，需要符合嵌入模型的使用要求。

固定 top-k 还存在边界：

- 空库不能正常提供证据。
- k 大于有效条目数时，必须处理缺失近邻标记；负数索引不能直接用于 Python 列表，因为 -1 会读取最后一项。
- 相近不等于相关，必须保留无答案状态。
- 返回向量顺序要和 chunk ID 一致，不能只假设所有接口都按输入顺序返回。

## 5. 证据应从字符串列表变成可核查记录

原课把 Python 列表表示放入 prompt，读者能看到文本，但没有稳定的来源ID与位置。工程补充可以保存：

```json
{
  "chunk_id": "essay-01:chunk-03",
  "source": "approved-document",
  "version": "document-hash",
  "text": "原文片段",
  "position": {"start": 4096, "end": 6144}
}
```

这里 position 是示意字符区间，具体坐标体系要保持一致。回答应引用真实 chunk_id，输出后检查引用存在、权限符合、结论由原文支持。不要让模型凭空生成一个看起来像引用的ID。

长上下文增加可放入的资料量，但不会自动修复错误检索或来源混淆。

## 6. Small 与 Large 的时延实验为何需要补充

原课两段代码打印 FizzBuzz 回答，没有计时器，也没有统一结果长度和多次采样。它们能展示不同回答风格，不能单独证明稳定的性能差。

若做性能实验，应记录：

- 同样的提示、工具定义、生成限制与版本。
- 输入和实际输出token数量。
- 首token时延、总时延、是否流式。
- 冷启动、排队、并发与失败重试。
- 任务成功率和时延分布。

长答案的总耗时可能更大，不等于每token更慢。代码生成还要用执行结果评价；写得漂亮不保证正确。示例提示要求 FizzBuzz，应覆盖3、5、15的倍数与边界输入。

## 7. tokenizer 对比能证明什么

课程用相同天气问题与工具定义编码两个模型请求，比较 token 数。这个计数包含聊天模板与工具Schema，不只是用户问题。

如果一个模型的token数更少，只能说明在该样本与该 tokenizer/template 配置中编码更紧凑，不能直接推出：

- 所有语言都更省token。
- 模型语义质量更高。
- 请求成本一定更低。
- 同一上下文长度承载的业务信息一定更多。

公平实验应保存输入、模型版本、tokenizer版本、特殊token与工具模板。增加中文、英文、代码、数字与长文样本，再观察分布。两个模型的token ID不能互换。

## 8. 如何迁移到自己的区域文档

以区域指标手册为例：资料记录指标定义、分母、时间粒度与正负向规则。先对定义做搜索评测，再让模型按检索结果解释；具体月份数据由业务接口提供，不让静态手册替代实时数据。

无证据时返回无法确认；定义冲突时标记版本冲突；用户权限不满足时，在检索前后均守住数据边界。详细实现参见第08、11与15课。

## 9. 自测

为什么本课 RAG 不能只通过“输出了一段韩文”验收？因为语言正确不证明回答来自证据。还应验证检索相关性、资料进入实际请求、来源权限、事实支持和无答案处理。

为什么一次token计数不能支持通用价格结论？因为价格单位、模型定价、模板和任务分布均影响总成本。
