# 第16课深化：开放模型的资产、许可与部署

> 对应 [第16课概览](../16-open-source-models.md)。核对日期：2026-10-04；上游快照：`d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8`。
> 本文是中文解释与工程补充，模型家族名称仅用于理解课程历史示例，不构成当前选型推荐。

## 1. 这一课真正解决什么问题

调用托管模型时，服务商隐藏了权重、推理运行时与容量管理。下载模型后，这些责任转移给应用团队。你获得更多控制权，也必须自己回答：这些文件是什么、是否可以合法使用、是否适合任务、如何复现一次推理、怎样持续运维。

“能下载权重”只是起点。开放权重、开放训练代码、公开数据、可复现训练和满足某种开源定义，是不同事实。不要仅凭仓库名称含 open 就判定许可允许商用、分发或任何用途。课程对开放程度的介绍适合建立问题意识；具体合规结论需要阅读目标版本的许可证与附加条款。

## 2. 下载的不是一个孤立的文件

| 资产 | 用途 | 缺失或不匹配的后果 |
|---|---|---|
| 模型权重与分片索引 | 存储学习后的参数，定位多个分片 | 加载失败或加载错版本 |
| config | 描述架构、维度、特殊 token 等 | 运行时无法解释权重 |
| tokenizer 与词表 | 文本和 token ID 相互转换 | 相同文字对应不同 ID，输出异常 |
| chat template | 把角色消息编码成模型训练时的格式 | 指令表现下降、角色边界混乱 |
| generation config | 默认生成参数 | 同一程序在升级后行为变化 |
| model card | 任务、语言、训练说明、评估与限制 | 把适用范围误当通用能力 |
| license 与使用条款 | 明确使用、修改、分发条件 | 权重可访问却无法按目标方式交付 |
| adapter | 在基座之上保存任务适配参数 | 配错基座或 revision 后失效 |
| processor | 多模态输入的预处理 | 图片尺寸、归一化、占位符不一致 |

工程补充：文件名相似不能证明兼容。发布清单至少记录模型仓库、不可变 revision、tokenizer revision、adapter 基座、量化方式、运行时版本与配置。对于下载时执行仓库自定义代码的模式，还应审查代码及其依赖；固定 revision 只能保证重复下载同一内容，不能证明内容安全。

## 3. 基座模型和指令模型为什么不一样

基座模型学习续写文本；指令模型经过额外适配，学习响应任务与对话。它们可能共享架构，却不能靠“加一句你是助手”互相替代。

假设需要提取合同编号：

- 基座模型可能继续写下一段合同正文。
- 指令模型更可能按要求返回字段，但仍可能编造缺失字段。
- 工程层必须检查 JSON、字段类型、编号格式和证据来源；模型家族和指令训练都不替代这些检查。

中文能力、代码能力、工具调用能力应分别评估。“某基准分数高”不等于在你的长文档、固定字段或拒答任务上可靠。

## 4. 如何阅读模型卡

先把业务需求变成验收条件，再看模型卡能提供哪些证据：

| 你的问题 | 需要查证的内容 | 应补做的实验 |
|---|---|---|
| 能否处理中文客服？ | 语言覆盖、训练说明、已知限制 | 中文术语、歧义、混合语言集 |
| 能否读完整合同？ | 上下文限制、位置相关评估 | 首中尾证据、截断和无答案用例 |
| 能否调用工具？ | 工具格式、模板、训练支持 | 缺参数、错误工具、危险参数 |
| 能否在目标设备运行？ | 权重格式、运行时兼容性 | 实际峰值内存和并发压力 |
| 能否商业分发？ | 许可证、附加条件、依赖许可 | 发布清单与许可审查 |

“支持很长上下文”只说明某种配置的输入能力，不能推导长文本中每条信息都会被正确利用。公开评测还可能使用不同提示、精度或采样方法，因此比较时必须保留测试条件。

## 5. 课程例子的适用边界

源课程举了 Llama 2、Mistral、Falcon 等例子。这些名称应当被理解为快照中的教学对象，而不是今日最新版清单。

尤其要注意：

1. 不能把某个混合专家变体的特性推广到整个模型家族。确定具体型号后，查看它自己的架构配置。
2. 可本地部署不等于零成本。权重存储、显存、CPU、带宽、故障处理、升级和评估都是成本。
3. 免除部分 API 按量费用，不代表总成本低于托管服务。低利用率设备可能让每次成功请求更昂贵。
4. 本地运行不自动保证隐私。日志、下载渠道、网络监听、外部工具和遥测仍需检查。

## 6. 一个可复现的部署流程

**需求定义**：固定任务、语言、结构化输出、时延与质量底线。   
**候选过滤**：排除许可、设备、上下文或模态不满足要求的版本。   
**离线评估**：先比较固定测试集中的任务成功率、拒答和格式通过率。   
**容量验证**：测量冷启动、首 token 时延、生成速度、峰值内存和并发。   
**灰度发布**：固定版本并建立回滚条件，监控真实错误类别。   
**持续复核**：升级模型、tokenizer 或量化配置后重跑同一评估。

建议用以下清单保存实验，不在清单中存 API 密钥：

```yaml
experiment_id: contract-extract-v1
model_repository: owner/model
model_revision: immutable-commit
tokenizer_revision: immutable-commit
runtime_version: exact-version
precision: fp16-or-quantization-config
chat_template_source: model-revision
dataset_version: heldout-v1
generation:
  max_new_tokens: 256
metrics:
  schema_pass_rate: measured
  task_success_rate: measured
  peak_memory_bytes: measured
```

这是元数据模板，`measured` 是占位符，不能拿它当实际性能记录。

## 7. 实战：评估一个内部问答模型

选择 50 条可复核问题作为早期试验集只是工程示例，不是统计充分性保证。覆盖有答案、无答案、证据冲突、术语缩写和权限不足。每条保存允许读取的文档、标准要点和必须拒答的条件。

对两个候选模型使用相同检索结果、模板和输出预算。先分离“检索没有找到证据”和“有证据但生成错误”，再讨论模型能力。否则你可能换了更大的模型，却没有解决索引遗漏。

**验收产物**：候选版本清单、许可记录、失败分类、设备测量和回滚方案。仅保存几段看起来流畅的回答，不足以支撑部署决策。

## 8. 自测

- 权重文件和 tokenizer 能否独立任意替换？为什么？
- 同样的模型名称为什么还需要记录 revision？
- 指令模型生成合法 JSON，是否足以允许执行里面的工具参数？
- “本地且开源”为什么不能推出“安全且便宜”？

参考答案：资产存在配套关系；版本决定实际内容；格式合法不代表权限和业务条件满足；运行环境、许可、日志与总体成本仍需要独立验证。
