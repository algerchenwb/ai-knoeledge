# 07 · 聊天应用深化：上下文、会话状态、定制与评测

> 基于第07课的中文解读；「工程补充」为原创设计。核对日期：2026-10-03。所有业务数据均为虚构。

## 1. 多轮聊天比单次生成多了什么

单次生成可以只处理一个完整问题，多轮聊天还必须解释“那里”“同样条件”“改成工作人群”对应什么。

例子：

1. 用户：查询 A 商场 2026年9月的客流画像。
2. 用户：换成工作人群。
3. 用户：再看8月，比较一下。

第三句不是独立问题。正确结果需要保留地点、更新月份、保留第二轮的人群类型，并明确比较的是同一地点工作人群在8月与9月的画像。

如果只发送第三句，模型无法知道这些条件。模型的“记得”来自应用提供的上下文或服务管理的会话状态，不是它自动知道你数据库里的全部历史。

## 2. 原课程的 Chatbot / Chat application 区分

课程把 Chatbot 描述为更聚焦固定任务的机器人，把生成式聊天应用描述为更重视上下文和交互的系统。这是教学上的比较，行业实际用词可能重叠：一个 Chatbot 也可以采用生成模型和多模态功能。

更实用的划分是：

| 形态 | 用户目标 | 必要能力 |
| --- | --- | --- |
| FAQ 助手 | 找到固定问题的答案 | 资料检索和依据 |
| 数据助手 | 获取并解释业务结果 | 实体解析、参数、权限、查询 |
| 执行助手 | 完成一项操作 | 工具校验、状态与副作用控制 |
| 开放聊天 | 连续讨论主题 | 历史、边界和用户体验 |

有对话历史不等于有执行权限。有工具调用不等于所有操作都可以自动执行。

## 3. 三种状态不要混为一谈〔工程补充〕

**消息历史**保存谁说了什么，用于审计和还原交流。

**业务状态**保存已确认的地点、时间、人群、指标和任务进度。这些字段应经过校验，不能简单把上一轮模型生成的话当成事实。

**长期偏好**保存经产品规则允许的稳定偏好，例如输出语言。临时说“这一次简短点”不应自动变成永久设置。

可以用下面的结构理解一个会话：

```json
{
  "conversation_id": "example-session",
  "business_state": {
    "region_id": "example-region-A",
    "population_type": "work",
    "comparison_months": ["2026-08", "2026-09"]
  },
  "last_data_status": "validated",
  "pending_ambiguities": []
}
```

conversation_id 只是定位信息，不是访问凭据。服务端必须确认当前用户对该会话拥有权限，不能允许凭会话 ID 读取他人的内容。

## 4. 一轮对话的安全状态更新

建议按以下顺序执行：

1. 校验用户与会话归属。
2. 读取已确认业务状态。
3. 将用户新消息解析成增量变更。
4. 检查实体歧义、字段类型与跨字段冲突。
5. 通过校验后形成新的查询条件。
6. 调用数据接口并校验结果。
7. 生成回答，记录完成或失败。

“换成工作人群”是对 population_type 的变更，不是对所有字段重置。如果用户说“重新开始”，则按产品规则清空任务状态。

如果上一轮查询失败，下一轮“那个结果”不能引用一份不存在的结果。状态里要区分请求参数已确认与数据成功返回。

### 简单的状态变更代码〔原创可运行示例〕

```python
import re

ALLOWED = {"region_id", "month", "population_type"}
PEOPLE = {"resident", "work", "regular", "visitor"}

def apply_patch(state, patch):
    if not isinstance(patch, dict) or not set(patch) <= ALLOWED:
        raise ValueError("变更字段非法")
    candidate = dict(state)
    candidate.update(patch)

    month = candidate.get("month")
    if not isinstance(month, str) or not re.fullmatch(
        r"[0-9]{4}-(0[1-9]|1[0-2])", month
    ):
        raise ValueError("月份非法")
    if candidate.get("population_type") not in PEOPLE:
        raise ValueError("人群类型非法")
    region = candidate.get("region_id")
    if not isinstance(region, str) or not region.strip():
        raise ValueError("区域缺失")
    return candidate
```

该示例返回新状态而不修改原状态，所以失败不会污染原对象。它只验证语法，不证明 region_id 存在，也没有实现权限、月份业务范围或实体解析；这些应由后端完成。

## 5. 为什么不能把全部历史无限发送

历史越长，成本与等待时间通常越高，也可能挤掉当前事实。旧请求中的错误结果和已经失效的条件还会影响新回答。

可采用“近期消息 + 已确认业务状态 + 必要历史摘要”。摘要是压缩信息，不是可靠数据库，需要特别保留：

- 已确认实体与候选歧义；
- 时间基准、统计月份和人群；
- 指标定义与单位；
- 用户明确撤销或修改的条件；
- 已执行工具及其成功或失败状态。

例如摘要把“8月居住人群、9月工作人群”压缩成“比较8月与9月画像”，就丢了关键的不可直接比较条件。结构化状态比自由文本摘要更适合保存这些字段。

检索长期记忆时也要按权限过滤，不能全用户共用相似度召回结果。

## 6. 系统说明怎么写

课程提出四类内容：适用对象及能力边界、输出格式、期望行为示例、额外行为限制。可映射为一个数据助手的规则：

```text
对象：需要查看区域画像的业务用户。
能力：解释已提供且通过校验的聚合统计。
限制：不推断个人属性，不猜测缺失指标，不自行编造区域 ID。
输出：先给业务结论，再给统计时间、口径、来源和缺项。
示例：无数据时说明“当前查询没有返回有效统计”，不能说“人数为0”。
```

规则是模型行为指引，不是鉴权机制。用户资料、检索文档和工具返回值都要按来源处理，不能允许其中的文本修改后台权限。

## 7. 领域定制：提示词、RAG、工具与微调

课程谈到领域语言与微调，并用医疗场景说明通用模型可能缺乏专业性。本知识库进一步区分：

| 需要解决的事情 | 通常先考虑 | 原因 |
| --- | --- | --- |
| 固定术语和格式 | 提示词与示例 | 低成本验证行为 |
| 解释企业文档 | RAG | 能提供可更新资料和来源 |
| 获取实时数据 | 工具/API | 使用真实业务系统 |
| 改善大量同类任务行为 | 微调与评测 | 通过训练改变任务表现 |

课程使用“DSL model”讨论领域模型，但 DSL 在软件工程中通常指领域专用语言，例如业务规则语法；它不是所有领域语言模型的统一标准名称。

微调不能自动保证知识最新，也不能自动提高到足以承担所有专业判断。先明确是“缺知识”“缺数据”还是“行为不稳定”，再选择方法。微调后的模型仍需来源、权限、输出检查与回归评测。

## 8. 评测指标不能照单全收

课程列出 uptime、response time、precision、recall、F1、perplexity 和用户满意度等。它们覆盖不同任务，不能全部机械套用。

**分类任务**可以定义 TP、FP、FN，然后计算：

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 × Precision × Recall / (Precision + Recall)
```

分母为零时应事先约定计算与报告方式。开放问答没有天然的正负标签，不能只因为模型答了一段话就计算 F1。

**生成任务**更适合看事实依据、任务完成、格式有效、错误拒绝、遗漏条件等。**检索任务**可看相关资料是否在前 k 条中召回。**执行任务**需要评估工具是否正确、权限是否合规、是否重复副作用。

Perplexity 描述模型对文本的概率预测表现，不能直接代替业务正确率，而且一些服务不提供计算它所需的概率信息。

推荐把技术指标和业务指标一起看：首个可见片段耗时、完整完成耗时、有效任务完成率、证据支持率、单次有效任务成本。用户满意并不总意味着事实正确，两者需要分别评估。

## 9. 并发、重发与多端操作〔工程补充〕

同一会话里可能同时到达“换成工作人群”和“改成8月”。如果两个请求都从同一个旧状态开始，后写入的请求可能覆盖前一个。

简单产品可以按会话串行处理；复杂产品可采用版本号进行并发控制。提交更新时检查 state_version 是否仍然匹配，不匹配就重新合并或明确冲突。消息顺序应由服务器记录，不能只依赖客户端时间。

网络重发还可能重复查询或执行操作。为一轮请求提供幂等键，并记录运行状态，有助于识别同一请求的重发。涉及副作用时，幂等应落实在执行端，不只是聊天记录里去重。

## 10. 用户体验与可访问性

- 对含糊实体展示候选，让用户看见系统正在比较什么。
- 显示所用地点、月份和人群，便于发现继承条件错误。
- 允许纠正、取消、清空当前任务。
- 明确显示结果来源与统计时间。
- 支持键盘操作、屏幕阅读、可调整文字与清晰语言。
- 长输出分段展示，但避免只有视觉动画提示状态。

这些设计帮助用户掌控任务，并减少“模型看起来答得很快，但实际上查错条件”的问题。

## 11. 练习与参考答案

1. 用户说“看那里8月的”，没有前文，怎么办？返回缺少地点，不猜。
2. 用户修改人群后，需要重查数据吗？需要，不能把旧结果换个标题。
3. 模型答错的月份进入了摘要，怎样避免继续污染？由已校验业务状态提供月份，摘要不能覆盖它。
4. 聊天满意度很高，能否证明正确率高？不能，应单独核验事实与任务完成。
5. region_id 语法正确就可查询吗？不能，还需确认存在性、归属和权限。
