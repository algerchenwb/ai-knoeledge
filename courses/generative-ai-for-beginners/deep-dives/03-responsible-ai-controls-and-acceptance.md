# 第03课深化：将负责任 AI 转成验收与运行机制

> 对应 [负责任 AI 概览](../03-using-generative-ai-responsibly.md)。核对日期 2026-10-04；上游快照 d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8。
> 本文是工程实践解释，不构成对某地区法律或某平台合规条件的判定。

## 1. 原则要落实成行为

课程提出公平、包容、可靠与安全、隐私与安全防护、透明和问责。只在 README 写出这些词，不能说明产品已经满足要求。每项应映射到具体风险、可观察行为、验收方法和责任人。

| 原则 | 具体问题 | 可执行措施 |
|---|---|---|
| 公平 | 相似请求因无关属性得到不同待遇 | 分组评测、检查代理特征 |
| 包容 | 语言或辅助技术用户难以完成任务 | 多语言、可访问性和恢复测试 |
| 可靠安全 | 错误建议影响用户行动 | 证据、验证、拒答与升级处理 |
| 隐私防护 | 数据跨租户或进入不必要日志 | 最小化、授权和脱敏 |
| 透明 | 用户不知道答案依据和限制 | 来源、更新时间和明确状态 |
| 问责 | 事故发生无人负责 | 审计、负责人、处置与回滚 |

以上是原创工程映射，不是统一认证标准。

## 2. 幻觉、危害与不公平并不相同

幻觉涉及缺少事实依据、错误或虚构内容。危害还可能来自事实正确但被错误使用的内容，或自动执行了本不应执行的动作。不公平可能来自训练偏差、数据覆盖不均、产品流程或业务规则，不能全部归到模型文字。

例如学习助手可以虚构参考文献；客服助手可以泄露其他用户真实资料；推荐系统可以因为覆盖不足对某些地区持续无结果。这三者需要不同调查与措施。

## 3. 不要继承问题中的错误前提

课程用历史问答说明：用户问题本身可能包含错误假设，模型却顺着前提给出流畅回答。关键能力是识别并说明前提无法成立，而不是努力填出一个名字。

工程补充：在测试集中加入“唯一”“全部”“一定因为”等强断言，但资料并未支持的请求。预期结果应纠正或限定前提，再提供可确认内容。不要用提示词要求每个问题都给出确定答案。

## 4. 用风险登记表组织工作

```yaml
risk_id: evidence-mismatch-001
scenario: report-generation
failure: explanation uses a value absent from authorized evidence
impact: user may make a wrong business decision
controls:
  - restrict data by trusted identity
  - validate output values against source payload
  - show source version and uncertainty
owner: application-team
verification: heldout cases and incident review
residual_risk: explanatory causal claims may remain unsupported
```

这是教学模板，owner 需要在实际团队落实。风险记录既描述措施，也承认剩余风险。风险优先级可以结合影响、发生可能性、暴露范围和恢复能力，不宜只计算一个数字后机械排序。

## 5. 多层缓解怎样合作

**模型层**：依据任务选择模型，评估拒答与安全行为。微调可能改变行为，但不能保证风险只降低。   
**服务层**：认证、速率限制、内容检测、异常观察等控制。   
**提示与资料层**：清楚说明任务，分离指令与不可信资料，提供来源。   
**执行层**：验证工具参数、权限、业务前置条件、超时与预算。   
**体验层**：显示真实状态、提供纠正与人工处理路径。   
**运行层**：记录事故、发布回滚与定期复评。

课程强调模型、安全系统、metaprompt 和体验层。本文增加执行与运行的具体边界。某层通过不能代替其他层：内容过滤不能检查数据库租户权限；RAG 不能保证模型一定依据证据；提示词不能撤销工具权限。

## 6. 公平测试要选择相关切片

对多语言教育助手，可以按语言、阅读水平、输入表达方式或可访问性需求切分任务。比较完成率、错误类型和无理由拒答，核对样本数量及任务难度。

不同群体的平均分不同，不自动证明原因；平均分相同，也可能掩盖某些高影响错误。需要查看具体失败与数据覆盖，并避免为测试无必要地采集敏感属性。

对于区域分析，应区分“资料不足”和“表现差”。模型不能因为某区域数据少就把它描述成商业价值低。缺失应标为缺失，不能擅自填零或编造判断。

## 7. 安全性与可用性一起评估

只统计拦截率会遗漏正常请求被误拒。至少区分：

- 正常请求成功。
- 有风险请求被合理限制。
- 正常请求被错误拒绝。
- 有风险请求被错误允许。
- 无法确定、需要进一步核查。

拒答时解释与当前请求相关的限制，并给出可行下一步。不要只显示模糊错误，也不要暴露过滤器内部策略或敏感资料。

## 8. 透明不是展示所有内部信息

用户需要知道答案依据、信息日期、计算口径、是否完成与如何纠正。公开系统提示、密钥、内部网络或其他用户数据不是透明要求。

例如区域报告应说明：统计月份、允许的数据来源、是否缺失、数值计算规则和原因分析证据。生成的一句“仅供参考”不能代替这些内容。

不要把模型自由生成的自信程度当作校准概率，也不要用“已验证”标签覆盖实际上未做的核验。

## 9. 从上线前测试到事故处理

上线前建立正常、边界、攻击和回归用例，记录版本与验收责任。上线后观察用户纠正、拒答、异常输出、工具失败和权限拒绝。

发生事故时：

1. 限制受影响能力，保留必要且脱敏的证据。
2. 确认影响范围：模型版本、资料、用户、操作回执。
3. 修复相应层并增加回归用例。
4. 验证修复、恢复服务，记录负责人和剩余风险。

不要把重试或模型升级当成所有事故的共同修复。错误来自资料污染时，应处理资料及索引；来自授权时，应修服务端权限。

## 10. 原课程需要限定的表述

- 更大模型不必然更危险，小模型不必然更安全；依任务与实际评测判断。
- 微调不保证降低有害输出，应比较适配前后。
- 把资料加入 RAG 不保证模型只使用可信资料，仍要检查引用和结论。
- 原课知识检查把正确性与危害分开列出，但事实正确性也关系可靠性，不能理解成负责任 AI 不需要关注准确性。

## 11. 练习

给区域洞察 Agent 列出三项风险：跨租户读取、原因解释无证据、月份或分母混淆。每项填写触发条件、检测方式、执行控制、用户反馈和负责人。然后分别设计正常用例与失败用例。

答案方向：租户边界由可信身份和数据服务检查；原因解释只使用可核查依据；月份与分母进入结构化契约并独立验证。
