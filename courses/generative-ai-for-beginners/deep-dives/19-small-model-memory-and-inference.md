# 第19课深化：小模型的内存、量化与推理验收

> 对应 [第19课概览](../19-slm.md)。上游快照 `d8ec07e31c4b32bd283d565c1abd9b58bb5cf2e8`；核对日期 2026-10-04。
> 本文中的数值是理论示例，未下载或运行模型，也没有测量用户设备。

## 1. “小”是相对的，不是能力保证

SLM 通常表示相对较小的语言模型，并没有跨所有场景通用的参数量门槛。小模型可以直接训练，也可以蒸馏或采用其他压缩方法；不能把所有小模型都描述成大模型压缩产物。

参数更少可能降低计算和存储需求，但实际速度取决于硬件、算子、量化后端、上下文和并发。小模型也不天然更少偏见或更安全。任务正确率应以目标场景验证。

课程中的 Phi 系列用于展示小模型、多模态和混合专家的思路。专有模型的参数规模或内部架构若没有可靠公开依据，不应根据课程对比图推断为确定事实。

## 2. 先算权重，再考虑运行开销

理想密集权重存储：

```text
weight_bytes = parameter_count × bits_per_parameter / 8
GB = bytes / 1,000,000,000
GiB = bytes / 1,073,741,824
```

| 教学示例 | 理想权重字节 | 十进制 GB | 二进制 GiB |
|---|---:|---:|---:|
| 7B、16 bit | 14,000,000,000 | 14.00 | 13.04 |
| 7B、8 bit | 7,000,000,000 | 7.00 | 6.52 |
| 7B、4 bit | 3,500,000,000 | 3.50 | 3.26 |

这些数值不包括量化尺度、零点、未量化模块、对齐、激活、KV cache、临时张量和运行时开销。不能据此宣称“4GB 显存一定能运行 7B 4bit”。

下载文件大小、CPU 常驻内存、GPU 常驻内存与峰值内存也不是同一指标。加载过程可能短暂同时保存多个副本。

## 3. KV cache 为什么随上下文增长

自回归生成保存历史 token 的 key 与 value，避免每一步重复计算全部历史表示。普通 decoder 注意力的一个基础缓存估算是：

```text
kv_bytes ≈ B × T × L × 2 × H_kv × D × S
B: 有效批量
T: 保存的 token 数（输入与已生成 token）
L: 层数
2: key 与 value
H_kv: 每层 KV 头数
D: 每个头的维度
S: 每个缓存元素的字节数
```

工程推导示例：B=1、T=4096、L=32、H_kv=8、D=128、S=2，则缓存为 536,870,912 bytes，即 0.5 GiB。上下文翻倍或批量翻倍时，其他条件相同，缓存也翻倍。

注意 H_kv 不一定等于 query head 数；分组查询注意力可能使用更少 KV 头。滑动窗口、混合层结构、缓存量化、分页和 offload 会改变实际存储方式与峰值。这条公式只估算指定假设下的原始 K/V 数据。

[Hugging Face 缓存文档](https://huggingface.co/docs/transformers/kv_cache)说明缓存有不同实现及内存取舍。权重量化也不意味着 KV cache 自动采用相同位宽，必须检查运行时配置。

## 4. MoE 与多模态的额外边界

混合专家（MoE）的“每个 token 激活参数”描述计算路径，不能直接当作所有权重的驻留大小。未参与当前 token 的专家仍可能存储在设备或内存中；offload 会引入传输成本。

视觉语言模型还需要图像处理器和视觉相关模块。图片分辨率、裁剪、patch 数或视觉 token 会影响输入长度和内存。接受多张图片不等于自动支持连续视频理解；需要明确帧采样、时间信息与模型输入协议。

## 5. 量化该怎样验收

量化用更低精度表示参数或缓存以降低资源需求。效果取决于方法与任务，不能只检验模型能启动。

| 验收维度 | 重点用例 |
|---|---|
| 中文质量 | 领域术语、数字、否定与歧义 |
| 结构化输出 | JSON、枚举、缺失字段 |
| 工具参数 | 数值边界、对象 ID、拒绝越权 |
| 长文证据 | 首中尾引用、无证据拒答 |
| 数值任务 | 单位转换、精确抽取 |
| 性能 | 冷启动、峰值内存、首 token 和吞吐 |

应比较实际部署的量化产物和未量化基线，使用相同测试输入。模型成功加载不等于量化后质量通过。

## 6. 分清 prefill 与 decode

**Prefill**：处理输入提示，建立初始状态与缓存。输入越长，首 token 延迟可能越大。   
**Decode**：逐步生成新 token，通常关注单流生成速度和并发吞吐。   
**端到端时延**：还包括排队、加载、检索、模板处理和网络传输。

单用户 tokens/s 高不代表并发服务体验好；批处理可能提高整体吞吐却增加排队。至少记录输入长度、输出长度、并发、精度、设备、是否热启动和采样设置。否则两个测试结果不可直接比较。

## 7. 运行时选择与 WSL 检查

课程涉及 Transformers、Ollama、Foundry Local 与 ONNX Runtime GenAI 等路径。它们对应不同的模型格式、平台和后端，具体支持范围随版本变化。应先确认目标模型与硬件的兼容性，再按相应版本官方文档安装。

在 WSL 场景中，Windows 能识别 GPU 不证明 WSL 内推理程序已使用 GPU。需要在实际运行环境核对设备可见性、驱动兼容性、运行时后端与实测利用情况。下载与转换也可能占用大量磁盘及临时空间。

不要把“支持 CPU 推理”解释成无需评估性能；也不要把某些示例依赖 GPU 的现象解释成所有小模型都必须 GPU。

## 8. 本地部署的隐私与服务边界

工程补充：检查监听地址、访问控制、日志保存、外部工具、模型下载和运行时遥测。服务监听所有网卡时，局域网或其他容器可能访问它，具体取决于网络与防火墙配置。不要默认本地服务就只对当前用户开放。

将文件、数据库和写操作的权限放在应用执行器，模型只接收任务需要的数据。本地模型同样可能受到不可信文档提示注入影响。

## 9. 离线计算练习

随附 [内存估算检查](../examples/deep_dive_model_memory_checks.py)验证单位、基础权重公式、KV 缓存增长与无效参数。它仅使用 Python 标准库，不下载模型。

```bash
python courses/generative-ai-for-beginners/examples/deep_dive_model_memory_checks.py
```

计算顺序：

1. 从具体模型配置取参数数、层数、KV 头数与 head_dim。
2. 按部署精度估算原始权重。
3. 按目标批量与上下文估算普通 KV cache。
4. 列出未计入的量化元数据、激活、临时张量和其他模块。
5. 在实际设备上测峰值，并建立并发和上下文上限。

仅凭前两步不能判定设备是否足够。

## 10. 自测

- 7B 4bit 的 3.5GB 为什么不等于运行所需显存？
- 为什么不能用 query head 数无条件代替 KV head 数？
- MoE 的激活参数为何不等于加载权重？
- 同一模型在两个运行时的速度为什么需要重新测量？

答案方向：运行时有额外内存；注意力结构不同；专家存储与执行不同；算子、设备、调度和配置影响性能。
