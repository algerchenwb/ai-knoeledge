# 08 · Embedding 与语义搜索

> 原课程解读与中文重写；「工程补充」为额外实践。核对日期：2026-10-03。

## 语义搜索解决什么问题

关键词搜索匹配词面，语义搜索尝试匹配意思。“如何避免 pod 内存不足”与“OOM 排查”词面不同，却可能讲同一件事。Embedding 将文本映射为一串数值，用向量距离或相似度寻找接近的内容。

它是可计算的表示，不是模型给每段文字人工贴上的标签。向量相似只意味着某种相关性，不等于逻辑等价、事实正确或完全符合业务约束。

## 原课程的视频搜索案例

课程将视频转录切成三分钟片段，保留约二十词的重叠，提取讲者并生成摘要，为片段生成向量，将片段、时间与链接写入索引。用户问问题时也生成向量，再检索相关片段，返回可定位的原视频。

三分钟、二十词及示例向量维度是该案例配置，不是通用标准。文章、API 定义与中文文档应按结构和模型 tokenizer 调整。

## 两条链路

离线链路：采集 → 清洗 → 切分 → 向量化 → 保存索引和元数据。

在线链路：问题标准化 → 编码查询 → 按权限筛选并检索 → 排序 → 返回片段和来源。

索引必须保存原文或可恢复的原文引用。生成回答时通常传入文本片段，不是把数千个向量数字塞给语言模型。

## 余弦相似度

cos(a,b) = (a·b) / (||a|| ||b||)，比较向量方向接近程度；零向量需要特殊处理。余弦数值不是“答案正确的概率”。不同模型和内容分布下分数尺度不同，不应共用一个拍脑袋阈值。

欧氏距离通常越小越近；相似度通常越大越近。向量库的 score 可能经过变换，读取文档确认方向，防止反向排序。

## Chunk 的作用〔工程补充〕

Chunk 是检索的最小内容单位。过大容易混合多个主题，过小容易丢上下文。对 API 文档，适合把接口用途、参数与限制保留在一起；对长文档，可以按标题和段落切分，给片段附上章节路径。

~~~json
{
  "chunk_id": "api-location-v2#limits",
  "text": "位置查询的参数与限制……",
  "source": "docs/location.md",
  "version": "v2",
  "tenant_id": "demo",
  "updated_at": "2026-10-03",
  "embedding_model": "example-embedding-v1"
}
~~~

示例不含真实数据。版本变化时要更新或删除旧 chunk，避免新旧口径一起召回。

## 向量库与混合检索

内存数组足以验证小样本；生产系统可能需要近似最近邻索引、过滤、分片、更新与持久化。向量索引不是关系数据库替代品，日期、人群类型、租户和精确 ID 仍应结构化过滤。

纯向量搜索对接口路径、错误码、BSSID 等精确字符串可能不如关键词搜索。混合检索可以同时召回两路结果，再用排名融合或重排整合。分数不在同一尺度时不要直接相加。

## 如何验证搜索有效

给查询标注相关文档 ID，计算 Recall@k 和排名指标，再人工分析漏召回。区分“没有资料”“切分破坏资料”“编码不适合”“过滤错误”“排序错误”。不要只看返回结果长得像相关。

## 练习

建立 30 段脱敏接口文档，分别测试业务描述、精确路径和错误码查询。比较关键词、向量和混合检索。能指出每种方式的失败场景，比背诵向量库产品名更重要。
