# 14 · LLMOps 与应用生命周期

> 原课程解读与中文重写；「工程补充」为额外实践。核对日期：2026-10-03。

## LLMOps 是管理整个应用

原课将生命周期分为探索、构建增强、上线运营，并持续治理。与只训练一个预测模型相比，生成式应用需要一起管理模型版本、提示词、资料、工具、检索与输出验证。

同一个模型下，改 chunk 切分、工具描述或提示词也可能改变结果。因此“模型没有升级”不意味着系统行为没有变化。

## 从 PoC 到上线

| 阶段 | 需要得到什么 | 通过条件 |
| --- | --- | --- |
| 探索 | 明确任务、成功标准、基线 | 知道为什么需要 AI |
| 构建 | 可复现流程和评测集 | 关键失败可解释 |
| 增强 | RAG、工具或微调的效果对比 | 改动优于基线 |
| 运营 | 监控、回滚和错误恢复 | 能定位线上失败 |
| 治理 | 权限、数据和变更管理 | 谁负责清楚 |

课程介绍 PromptFlow 与 Microsoft Foundry 作为工具路径。思想可以迁移到其他框架：流程可观测、评测可复现、发布可回退。

## 一次请求记录什么〔工程补充〕

request_id、tenant 标识的安全表示、model_version、prompt_version、index_version、tool_version、阶段耗时、输入输出 token、终止原因与错误分类。内容字段按数据策略脱敏或不保存，不能为了排错无条件记录所有原文。

一次完整调用最好拆成 trace：参数解析 → 检索 → 重排 → 工具 → 生成 → 校验。这样能分辨到底是模型慢、数据库慢还是重试过多。

## 指标要分三层

业务层看任务成功率、可采纳率和错误造成的影响；质量层看参数准确率、检索命中、证据支持、格式合规；运行层看 P95 延迟、超时、限流与成功任务成本。

例如 95% JSON 合法并不意味着 95% 查询正确。字段值错、月份不对或口径混用都可能产生合法 JSON。

成功任务成本 = 这一类任务总花费 / 成功任务数。它把失败重试与额外工具调用纳入比较，通常比单次 token 单价更接近业务成本。

## 评测与发布

建立固定基准集、线上脱敏回归集和攻击边界集。训练集与测试集隔离。模型评分器需要定义评分规则并用人工样本校准，不能将评分模型当成绝对裁判。

每次只更改可解释的一组变量，跑回归后小范围发布。保留上个模型与提示词版本；索引切换也要能回滚，不能只回滚代码却保留已经变化的数据。

## 故障降级

工具超时可以返回已完成部分并明确缺项；模型不可用可以退到确定性查询结果或人工流程。不要静默换模型而不记录版本，也不要把失败转换成“查询为零”。

## 练习

给一个 RAG 服务列出上线门槛：业务质量、检索质量、延迟、权限、费用与回滚。门槛值应由业务风险决定，本知识库不为所有应用给出同一个正确率数字。
