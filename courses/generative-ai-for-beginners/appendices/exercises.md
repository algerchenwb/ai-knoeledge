# 练习与验收：怎样证明自己理解了

以下为自主练习路线。规模和指标是练习设计，不是所有项目必须使用的统一上线门槛。全部使用虚构或脱敏数据。

## 第一组：基础能力

| 练习 | 产物 | 验收 |
| --- | --- | --- |
| 环境与调用 | 可配置模型名的最小脚本 | 能区分导入、鉴权、模型不存在 |
| Token 与上下文 | 两类文本的 token 统计 | 说明 tokenizer 不同为何长度不同 |
| 选型 | 同一批任务的对照记录 | 成功率、重试、延迟与成本一起看 |
| 提示词 | 参数提取模板 | 信息缺失时不猜参数 |
| 高级技巧 | 直接提示与拆解对照 | 说明新增步骤的收益和失败点 |

## 第二组：对话与检索

设计四轮对话，至少两次修改参数。输出每轮状态快照和缓存失效记录。历史摘要中的旧实体不能覆盖用户最新指令。

建立 30 段文档，至少包含两个相近但不同的业务口径。分别测关键词、向量与混合召回。相关标签用文档 ID，人工确定，不能用生成答案是否等于某一句文本作为检索标签。

构造只有资料中存在的虚构事实。检查最终请求是否含该事实和来源 ID；撤掉资料后应说明无法确认。若不撤资料就始终答对，不能据此证明 RAG 数据流正确。

## 第三组：工具与 Agent

实现一个只读工具，覆盖完整参数、缺字段、非法月份、错误枚举、未知工具、越权和上游超时。

增加第二个依赖前一工具结果的工具，检查顺序。让模型反复提出同一调用，确认预算能终止循环。输出已完成部分与阻塞原因。

如果添加写工具，再测重复请求与响应超时。授权信息从可信身份取，不允许模型替换租户。先查执行状态再决定重试。

## 第四组：评估与运行

建立一份失败分类表：

| 失败类别 | 示例 | 主要修复层 |
| --- | --- | --- |
| 需求理解 | 把工作人群当客流 | 提示、语义口径、澄清 |
| 检索 | 找不到已有资料 | 切分、编码、过滤、排序 |
| 请求组装 | 证据没有传给模型 | 应用代码 |
| 工具 | 调错接口或参数 | 契约、注册表、路由 |
| 权限 | 可访问其他租户 | 后端授权与数据层 |
| 生成 | 无依据解释涨幅原因 | 证据约束与校验 |
| 运行 | 总超时、重复重试 | 预算、观测、恢复 |

每次优化前后对照固定样本，避免只看新加的成功例子。记录版本，保留回退配置。

## 自测问答

1. JSON 合法就代表查询正确吗？不代表，业务值和事实需要另外验证。
2. 向量最相近就代表文档相关吗？不一定，查询可能根本没有匹配资料。
3. 工具调用由谁执行？由应用或工具执行器；模型提出建议。
4. RAG 必须使用向量库吗？不必须，也可以使用关键词、结构化查询或组合检索。
5. 微调能稳定记住每天变化的数据吗？不适合替代持续更新的可信数据源。
6. 多 Agent 是否一定胜过一个 Agent？不一定，可能增加错误传播与成本。
7. 本地模型是否天然完全离线？不一定，工具、日志与下载路径仍可能联网。
8. 降低 temperature 能消除幻觉吗？不能，它控制采样而非证据正确性。
9. 无数据与零值能否合并？不能，含义不同。
10. 为什么检查 payload？因为模型本来就可能知道答案，最终文本不能证明证据已传入。

## 从练习到项目

将每项产物保留为文档、固定测试样本或可运行脚本。上线门槛要由业务风险、错误影响和允许成本确定。线上失败经过脱敏与审核后可加入回归集，再作为后续改进依据。
